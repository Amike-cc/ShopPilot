fix(invite): 快手邀约真机实测——修掉 3 个真缺陷（级联离屏 / 发送后弹窗 / 失败被当处理中）；发布 0.4.30

结论：快手邀约现在能真的发出去。实测「我的达人 → 邀约中」新增 21:26 待处理一条
（达人「星星」ID 233041797），与该轮运行时间、所选类目对得上。

缺陷 1：页面被遮挡时 rAF 停摆 → 类目级联弹层停在屏幕外
- 快手的「带货类目」是级联弹层，靠 requestAnimationFrame 定位；Chromium 在页面不可见/窗口
  被遮挡时停掉 rAF（实测 visibilityState=visible 下 rAF 触发 0 次、定时器正常），弹层永远停在
  初始的 -9999,-9999，子类整块在视口外 → 受信任鼠标点不到。此前报成「被 unknown 遮挡，请把
  店铺窗口拉宽一些」，把人往"窗口太窄"上引——实测与宽度无关（加到 1320 也一样）。
- 修法：① WebContentsView 与独立窗口都关掉后台节流（backgroundThrottling:false）；
  ② 把"元素在视口外"与"被遮挡"分开报，新增 TASK_TARGET_OUT_OF_VIEWPORT，消息直接给出矩形、
  视口尺寸与「先让店铺窗口处于前台再重试」的可操作建议。
- 也试过"离屏时降级为 JS 点击"，实测有害、已回退：JS 点击虽能触发，平台只记下一级类目
  （标记里没有子类），会被后面的校验拦下，把"点不到"变成"校验超时"，诊断更难。

缺陷 2：点「发送邀请」后平台弹「邀约提示」，没人点掉 → 抽屉永不关闭
- 实测：弹窗逐条列出"该商品与这位达人不匹配"（佣金率低于下限 / 体验分低于下限），
  按钮是「返回调整 / 继续发送邀约」。不点它抽屉永远不关、一条都发不出去；此前档案里
  postSendConfirmText 是空的，整轮卡在 waitForGone 白等 180s。
- 修法：档案新增 postSendConfirmTexts（可多条，逐个条件点击），快手登记
  ['继续发送邀约','确认']；并把"抽屉收起超时"独立成 postSendGoneTimeoutMs——不再用
  "有没有配确认框"去推（那样一配就把 180s 缩成 60s，反而让快手必然超时）。

缺陷 3：平台明说失败了，却被当成"平台还在处理"
- 快手发送失败时**故意留着抽屉**（让商家调整重试），所以"抽屉没关"既可能是失败、也可能只是
  平台在处理，waitForGone 区分不出来，只能含糊超时。
- 修法：新增引擎原语 requireTextAbsent（文案缺席断言，读型）：页面上出现指定文案即按 code
  如实失败并带上平台原文。快手在发送后、等抽屉收起之前插入这道断言。
  措辞按实测校准：那条弹窗叫「**部分**邀约发送失败」，同批 2 位里 1 位其实已进「邀约中」，
  所以错误码用 TASK_SEND_PARTIAL、提示明说"**本批其余人可能已发出**，别急着重发"——
  写成"未产生有效邀约"会让用户重发、造成重复邀约。
