## 抖店发票页「渲染被节流饿死」（2026-10-14 修复）

现象：抖店发票采集整轮失败，`步骤 4/13（readTable）TASK_SELECTOR_CHANGED: 超时未出现元素 table`，
四个方向全变 0 条。

排查过程（每一步都有证据）：

| 查了什么 | 结果 |
| --- | --- |
| 那页长什么样 | 外壳 + 四个页签正常，内容区**永久停在「加载中...」**，0 个 `<table>` |
| shadow DOM / micro-app | 已排除 |
| 它的接口 | **全部成功**：`merchant/scenes` 38KB `0000`、`subject/list`、`shop/status`、`record/statusMap` |
| 视口 | 正常（1054×757、visible、未隐藏） |
| 手动刷新 + 逐秒采样 | **45 秒时表格出现**（1 张表 / 160 行） |
| 采集任务（不挂调试器） | 等满 90 秒**仍不出表**（整轮 106 秒） |

差异点是**有没有挂 CDP 调试器**——挂上会解除渲染节流。应用自己的
`setBackgroundThrottling(false)`（`taskAwakeStores` 那条路）对普通表格够用，对**这个微前端不够**。

修复（三件事缺一不可，都在档案里声明）：

1. `warmReload: true` —— 首次加载渲染不出来，**再导航一次**当作预热刷新
2. `unthrottle: true` —— 读表期间挂调试器 + `Emulation.setFocusEmulationEnabled`，读完就摘
3. `readTimeoutMs: 90000` —— 实测要 ~45 秒才出表，默认 30 秒刚好差一点

结果：`发票采集 ·11121` **succeeded（60 秒跑完）**，四个方向出数，
「**平台给我开票**」**158 条 / ¥108,147.26**。

### 「平台给商家开票」四家实测结论（2026-10-14）

**各家叫法不同**——这是第一轮看漏的原因：

| 平台 | 这一向叫什么 | 结果 | 读取方式 |
| --- | --- | --- | --- |
| 抖店 | **平台给我开票** | ✅ 158 条 / ¥108,147.26 | readTable |
| 微信小店 | **申请平台开票** | ✅ 6 条 / ¥42.50 | readTable |
| 拼多多 | **申请发票** | ✅ 10 条 / ¥4,899.63 | **readCards**（新能力） |
| 快手 | —— | ❌ **没有这一向** | 见下方证据 |

另有两条同族方向也登记了：拼多多「申请记录（平台给商家开票）」（表格，0 条）、
快手「达人给我开票（未开票账单）」（独立页面，0 条）。

**微信小店其实是四个方向**（第一轮漏了第 4 个）：申请平台开票 / 给买家开票 / 给平台开票 /
**收佣金发票**。「收佣金发票」是**配置表单**（发票抬头 / 开票地址 / 期望发票类型 / 期望发票税率
+《收佣金发票协议》），没有账单列表 → 无可采数据行。

**拼多多的待开票账单是卡片、不是表格**：资金中心「发票管理」默认页签「申请发票」实测 10 张卡，
例如 `账单日期 2026年01/04/05/06月 | 待开票金额（元） 5657.37 | 开票主体 上海寻梦信息技术有限公司`
（「开票主体」是**平台自己的公司**）。类名带构建哈希（`BusItem_topTitle__3bA_R`）不能写死，
而 `readLabelValue` 只取**最短的那一个**匹配（`cands[0]`）、读不了列表 → 为此新增了
**`readCards` 步骤**（以文案为锚，每张卡读成一行，返回结构与 readTable 同构）。
金额自校验：`5657.37 + 287.81 + 0.02 − 1045.57 = 4899.63` ✓

**快手没有「平台给我开票」**（可复核）：把该模块前端包
（`kwaishop-seller-fund-tax-bill-pc/kmi.*.js`）的**路由表**全量挖出来后，含「给我开票」的路由
**只有一条** `/seller-issue-invoice`（菜单文案「达人/MCN给我开票」）。其余路由是
`/subsidy` 平台补贴开票页、`/talent-subsidy` 达人补贴开票页、`/self-operated-subsidy` 给自营店开票、
`/self-consumer-subsidy` 向消费者开票、`/distributor/invoice-manage` 快手快分销-发票管理、
`/pay-later-subsidy` 国补明细管理 —— **全是"商家开出去"，没有平台开给商家的那一向**。

> 排查工具的一个教训：**包搜索不是对所有平台都有效**。微信小店连当前 URL 路径
> （`bill/home`）和页面上确定存在的文案（`申请平台开票`）都搜不到——它的路由与文案在懒加载分块里。
> **所以每次用包搜索都必须先做对照实验**（搜一个确定存在的串）；对照失败就不能拿"没搜到"当结论。
> 快手那次对照通过，结论才成立。

## 审查修复（2026-10-15）

**五处**会把用户带偏的问题（四处显示假信息、一处污染导出），都先复现、再修、再实机确认：

### BUG1「本次没读到」在本来就没表的方向上误报（还会落进「有问题」筛选）

方向卡片上出现「本次没读到（时间）」，tooltip 写：
「**下面显示的是上一次成功采集的数据，不是本次结果**」——可微信小店「给买家开票」、
抖店「达人给我开票」这两个方向**从来没有数据**（档案 `measuredRows: 0`，页面本来就没表）。
那句 tooltip 是假话，店铺还会因此落进「有问题」筛选。

根因：采集侧写"空标记"时**没区分**「档案声明本来就没表」和「这次真没读到」，两者共用 `emptyNote`。

修法：给标记加**意图**——
- 采集侧（`task-runner` 的 `readTable` / `readCards`）：`emptyOk` 把关的空写 `expected: true`
- 读取侧（`shared/invoice-snapshot.ts`）：`expected` 的空**不进** `emptyNote`，只在 `expectedEmpty` 留痕
- 实机确认：修复后徽标全部消失（`badges: []`），两个方向干净地显示 0 条

### BUG2「5 条假逾期」+「1 条真超时漏判」

KPI 上的「已逾期」是拿去催单的数字，里面混了假的：

| 方向 | deadline 实际内容 | 修复前 |
| --- | --- | --- |
| 快手「给平台开票（未开票账单）」 | `2026-06-10(预计)` | ❌ 算成逾期（那是**预计生效日期**） |
| 抖店「给消费者开票」 | `超时未开票 已超时 21天36分钟07秒` | ⚠️ 真超时却**没算** |
| 拼多多「给买家开票」 | `2026-02-20 14:14:36 已逾期236天…` | ✅ 正确 |

根因两个：档案把快手「**阈值生效时间**」映射成了 `deadline`（它只是阈值生效日）；
解析函数只认「逾期 N 天」这一种写法。

修法：档案不再映射该字段（落进「其他信息」照常展示）；解析函数加「任何带**预计**的值一律不判逾期」
并补上「已超时 N 天」。**实机确认：逾期 15 → 11**（去掉 5 条假的，补上 1 条真的）。

### BUG3「操作」按钮列混进「其他信息」→ 污染导出 CSV

实测「操作」列里躺着的是按钮文案：`开票` / `申请开票` / `上传发票` / `录入发票` /
`提交发票 支付违约金 账单导出` / `导出明细 查看详情`。这些进了导出的「其他信息」列，
而那份 CSV 是交给代账/报税的——每行拖一句按钮文案纯属噪音。

修法：`mapSection` 不收集 `操作 / 操作栏 / 操作列 / 更多操作` 这类表头。实机确认已清除。

### BUG4 自动更新显示**假状态**：以为在每 3 小时刷新，其实一次都不会跑

界面上三处都在说"自动更新开着"：

| 界面说 | 实际 |
| --- | --- |
| 按钮「**关闭自动更新**」（= 认为正在自动） | `collection.autoEnabled = **false**` |
| 「已启用 4/4 家 · 上次触发 10/04 19:23」 | 调度器 `if (!isAutoCollectionEnabled()) return` → **永远不触发** |
| toast「已启动 4 个采集任务；**发票每 3 小时自动更新一次**」 | 同上 |

根因：`invoiceSchedule` 只看任务上挂没挂 `everyMs`，**没看自动采集总开关**
（`collection.autoEnabled`，2026-10-04 用户要求关掉的那个全局开关）。挂着周期 ≠ 会自动跑。

修法（三处一起）：
- `invoiceSchedule` 增加 `autoEnabled` / `active`：`active = 挂着周期 && 总开关打开`
- 面板文案分三态，中间那态明说「**已挂周期但不会自动跑**——自动采集总开关是关的（4/4 家挂着）」
- 「开启」时**连总开关一起打开**（否则点了也不会跑）；一家都没挂上时把总开关退回去，不留"开着但不干活"
- 采集后的 toast 按总开关的实际状态说话

实机确认：面板从「已启用 4/4 家」变成「已挂周期但不会自动跑」；开关往返测试通过
（开启 → `autoEnabled=true` + 「已启用 4/4 家」；关闭 → 摘掉周期）。**测试后已把总开关还原为 false**
（用户要求的状态），任务周期也重新挂回原样。

### BUG5「金额占比」按**条数**算：结论正好看反

「按主体汇总」视图有一列「**金额占比**」，页面自己的说明也写着"金额占比一眼看出票压在哪个公司名下"。
但实现是 `pendingCount / 总条数`——**按条数**。两个指标会给出相反的结论，实测本机数据：

| 主体 | 按条数（旧，错的） | **按金额（新，对的）** |
| --- | --- | --- |
| 夏邑县唯衣美服装工作室 | 84% | **95.0%**（¥108,619.10） |
| 东阳市花小朵电子商务商行 | 4% | **0.1%**（¥95.97） |
| 未填写营业执照 | 11% | **4.9%**（¥5,562.15） |

也就是说"多张小票的主体"被画成大头、"一张大票的主体"反而不显眼——**正好看反**，差 50 倍。

修法：分母改成**金额**（与「可开金额」列、KPI 合计同一口径，都取自 `licenseSummary.amount`）；
总额 ≤ 0（整批退款冲正 / 全是 0 元）时不给比例，条只画最小宽度。另外这一列**只有条、没有数字**，
用户只能看个大概长短——给条补了 `title` / `aria-label`，写明确切比例与金额，
并注明"按金额，不是按条数"。修复后三个主体的占比相加 = 100%。

## 采集不再打断浏览器使用（2026-10-15）

**用户要求**：「采集数据的时候不要影响浏览器使用」。

**问题**：任务式采集（发票 / 涉税 / 主体）建的是**普通标签页**，而 `ensureRunTabForeground`
**每一步开头都会 `activateTab`** 把它切到前台。于是采集一跑，用户正在看的页面就被顶掉；
标签栏还每轮多出一个页（实测本机标签栏里积了 **40～52 个**采集留下的页）。

**根因**：平台从 **2026-10-02** 起就有完整的"采集专用页"能力，`window-manager` 里写着：

```ts
export function acquireCollectionTab(storeId): string   // 取（必要时建）采集专用标签页。不激活
export function releaseCollectionTab(storeId, tabId?)
```

它的注释里写的正是同一个诉求：

> 以前它直接用"该店铺的活动标签页"，于是每 10 分钟一轮的自动采集会把用户正在填的表单导航走
> ——**用户看到的就是"采集一跑，我的页面就跳了"**。

经营数据采集、产品同步早就迁移到了这条 API 上；**任务式采集一直没迁移**。

**修法**（`task-runner`）：
1. 纯采集任务 → `acquireCollectionTab(storeId)`：按店铺缓存、只建一个、**不激活**、
   不落库、不进标签栏（渲染层挂隐藏 webview，`opacity:0` 但保留布局盒 → guest 照常注册、
   页面内可见性判据照常成立）。**刻意不复用 `runTabByStore`**——那张表可能存着旧版本建的普通页。
2. `ensureRunTabForeground` / `activateTab` 对采集专用页**直接跳过**（它不需要前台）。
3. **含"用户要看着页面"步骤的任务仍然用可见页并切前台**：`waitForUserConfirmation`（用户要核对后
   确认）、`mirrorTabUrl`（门禁就是把页面镜像给用户看）。规则抽成 shared 的
   `shouldUseInternalRunTab`（纯函数），`tests/unit/run-tab-visibility.test.ts` 四条测试钉死——
   这条边界一旦改坏，表现是"用户对着看不见的页面点确认"，很难从界面看出来。

**验证状态（如实）**：改动已完成、`tsc` / `eslint` / `vitest`（119 文件 1267 用例）全绿、
构建通过；**但端到端验证被卡住**——本机那个正在运行的应用实例权限高于我的 shell
（`taskkill` / `Stop-Process` 都报 `Access is denied`），我无法重启它加载新代码。
需要用的人**手动重启一次应用**，我再跑 `tools/research/verify-collect-no-disrupt.mjs` 实测确认。

## 涉税信息报送（2026-10-14 追加，并入发票中心）

平台按《互联网平台企业涉税信息报送规定》（国务院令第810号）**按季度**向税务机关报送经营数据，
发票中心里新增「涉税信息报送」分区把它读回来。

### 默认「按主体统计」

平台报的是"**你这个纳税人**"的收入，不是"你这个店"的。同一家公司开在快手、微信、抖店的三家店，
在税务机关眼里是**同一个主体的一份收入**；只按店铺列，用户得自己拿计算器把几家的净额加起来，
很容易漏店或重复计。所以默认视图是**按主体统计**：

| 开票主体 | 纳税人识别号 | 涉及店铺 | 报送期数 | 期间范围 | 货物收入净额 | 服务收入净额 | 收入净额合计 | 主体核对 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

归组规则（`packages/shared/src/tax-subject.ts`，19 条单测，**代码优先**）：

1. 有纳税人识别号的 → 按识别号归组（大小写、空格、连字符都归一）；
2. 没识别号但名称与某个"有识别号的主体"完全相同 → 并进那个主体（平台偶尔只在部分期间给到识别号）；
3. 没识别号、名称也不匹配 → 按归一化名称归组；
4. 名称与识别号都没有 → 「未读到主体信息」桶，**绝不与任何真实主体合并**
   （把读不到主体的期间混进某个真实主体，等于替它虚增收入）。

每个主体都带**主体核对**结论：`与已填执照一致` / `还没填营业执照：X店` / `与执照不一致：X店`。
申报是按主体报的，"平台报的是哪家公司"和"你执照填的是哪家公司"不一致时，报出去就是错的主体——
这件事必须在申报前被看见。点「逐期明细」可下钻回原始报送期。

金额口径与别处一致：解析不出的期**不计入**合计并单独计数，绝不当 0 加进去。

**已实测**：

- **快手小店**（`/zone/fund/accounting/tax-information-submission`，2026-10-14）
  ——表头与数据分属两张 `<table>`；「销售货物/服务取得的收入」是**一格三段式文本**，采集后拆成三列。
- **抖店**（`/ffa/fxg-bill/tax-bill`「涉税信息报送数据」，2026-10-14）
  ——**地址不是猜的**：左侧导航 10 个分组里没有这个入口，是从抖店自己的接口流量里读出来的

  这页有三处与快手不同，都已在档案里处理：
  ① 表头是**合并单元格（colspan）**，7 个 `<th>` 实际占 11 列 → 用 `columns` **按列序**映射（列序真机逐格数出来的），同时保留表头文案校验；
  ② `tbody` 第一行又是**重复表头**，旧规则只拿第一行当词表时只命中 5/11（45%）→ 漏过 60% 阈值被当成数据；

  ——**唯一一个不读表格、改读接口响应的方向**。这页是 `<micro-app>` 微前端，子应用只渲染出外壳

  `settleAmount/refundAmount→结算金额/退款金额`（**单位是分**）。

### 三条如实原则

1. **平台用途限制必须与数据同屏**。快手该页原文写着这份数据
   「数据仅可作为您开展业务合作参考依据，**不得作为税务申报**、财务审计、监管备案等任何用途使用」。
   把数据摆到申报场景旁边却不带这句，等于应用在替平台背书——而平台恰恰说了不能用。
   所以这句话由主进程随接口返回（`disclaimer`），界面用红框渲染在数据上方，且不硬编码（单测钉住）。
2. **三段收入拆开、解析不出就是 `—`**。平台把「销售货物/服务取得的收入」做成
   `收入金额 / 退款金额 / 收入净额` 三段文本塞在一格里，界面拆成三列；
   解析不出的段显示 `—` 而不是 `¥0.00`，合计也不把它当 0 加进去。
   另有三段自洽校验（`金额 − 退款 = 净额`），对不上时标「数对不上」。
3. **「导出记录」没有当作可读表格**。该页的「导出记录明细」是一个**动作按钮**
   （点了会在平台侧真的生成导出任务），不是可读的表格页签——因此没有为它登记锚点，
   也没有伪造一个空表。要采集它需要先在真机上确认它跳到哪个页面。

### 口径细节

- **不设 `measuredRows`**：这张表的行数 = 该店过了几个报送期，随经营时长增长。
  拿固定条数当"比实测少"的阈值，会把经营 3 个月的店永远报成抓漏。
- **不挂自动更新周期**：发票是每 3 小时刷新，而报送数据按季度更新，3 小时一轮没有意义。
- 采集任务名前缀 `涉税报送采集 ·`（与发票同样"认领同一个任务"，不堆同名任务）。

## 设计目标

商家打开这一页只想回答四件事，界面的全部结构都为这四件事服务：

1. 这个月**要给哪家公司**开多少票？→ 主体分账是第一级结构，不是筛选器角落里的一个胶囊
2. **哪几家店**有票要开、哪个方向还没开？→ 店铺卡 + 方向卡两级下钻
3. 有没有**过期或临期**的？→ KPI 第 4 张卡 + 明细表里的逾期胶囊
4. 怎么**交代账**？→ 按主体导出，导出范围写死在确认框上

同时守住项目既有的两条红线：**只读**（不代提交开票）、**诚实**（读不到就说读不到，绝不用推测数据填满界面）。

### 1. 开票主体分账栏（新增的一级结构）

发票按营业执照开，不按平台账号开；同一执照下常挂好几家店。
把主体提成独立一栏，每项显示 `店铺数 · 待开票条数 · 可开金额`，底部一条进度条表示**该主体在全部待开票条数中的占比**——申报时一眼看出票都压在哪个公司名下。

- 选中态：品牌紫底 + 紫边；`未填写营业执照` 单独用警示黄底 + 「待补录」标
- 底部固定「获取主体营业执照」，附一句口径：只填空缺、不覆盖你已填的值
- 排序沿用 `groupStoresByLicense`：店多的在前、名称序、`未填写` 永远最后

### 2. 采集状态条

一行说清「这批数字是什么时候的、覆盖了几家、哪几家没读到」：

`● 最近采集 今天 17:12:04 · 覆盖 4/5 家店` + `每 3 小时自动更新 · 下次 20:12`
+ `1 家登录态失效 → 去登录`（红、可点）+ `1 家店未填营业执照 → 去补录`（黄、可点）
+ `1 条金额无法解析，未计入合计` + `40 条无需操作（不计入待开票）`

**为什么必须有这一行**：采集失败与「确实没有发票」在屏幕上长得一模一样，是这类工具最危险的静默错误。状态条把「这次没读到」与「本来就没有」在视觉上彻底分开。

### 3. KPI 四张卡（跟随选中主体收窄）

| 卡片 | 值 | 注释 |
| --- | --- | --- |
| 待开票条数 | 17 | 覆盖 4 家店 · 另 40 条无需操作 · 全部主体共 17 条 |
| 可开金额合计 | ¥2,026.40 | 1 条金额未解析，未计入 |
| 有票待开的店铺 | 4 / 5 | 其余店铺无待办或登录态失效 |
| 时间风险 | 1 条已逾期（红） | 3 条 3 日内到期 |

**设计决策**：KPI 跟随左侧选中的主体，而不是永远显示全局。点了「未填写」还看到 17 条会让人以为筛选没生效；全局数放在卡片 1 的注释里做交叉印证。工具条右侧同时写明「口径：全部主体 · 显示 5 / 5 家店」。

### 4. 店铺卡 + 方向卡 + 明细表

店铺卡头部：平台徽标（各平台品牌色圆点）· 店铺名 · **主体标签**（点击行内补录）· 采集时间与登记的档案 · 右侧 `待开票 N 条 · 无需操作 M 条` + 打开发票页。

主体核对行：左边「开票主体 = 你填的」，右边「平台读到的主体 + 逐字段结论」。当前只有快手小店实测了主体信息页，其余平台如实写「暂未实测到可读的主体信息页——不猜、不填」。

方向卡（一个平台的开票方向 = 一张卡，实测微信 3 个、抖店 4 个、拼多多 2 个、快手 3 个）：

- 徽标三态：`待开票`（橙）/ `无需操作`（灰，带原因 title）/ `无记录`（灰）
- 大号条数 + 金额；**无需操作的方向金额置灰**，并在右下角标「不计入待开票合计」
- 角标：`本次没读到`（本次采集失败、显示的是上一次数据）· `比实测少（N）`（读数少于档案登记条数，可能抓漏）· `N 条金额未解析`
- `查看明细` 展开整行宽的明细表（统一列：单号/账单号 · 期间/申请时间 · 类型 · 可开金额 · 发票抬头/收票方 · 税号 · 状态 · 承诺/到期；`承诺/到期` 列在该方向无值时不渲染）

状态胶囊：`待开票` 橙、`已开票/审核通过` 绿、`逾期` 红并带天数、`待处理` 蓝。

### 5. 按主体汇总（视图切换）

申报与交代账直接看这张表：一行一个主体，含 `包含店铺 · 待开票 · 可开金额 · 金额占比条 · 无需操作 · 金额未解析` 与「导出该主体」。底部合计行。

### 6. 平台覆盖与金额口径

四个平台卡（页面路径 + 方向数 + 已实测标记）配四条口径说明：待开票 ≠ 全部记录、金额口径按各平台页面为准、解析不出就不计入、只读。

## 落地前建议的一处数据改动

设计稿按「**平台给我开票 / 达人给我开票**」标为 `无需操作`（不计入待开票合计）绘制——这两类是平台或达人开给商家的票，商家确实没有待办动作。

`pending: false` 与 `notPendingNote`。这是**数据侧**的改动，界面侧不用改——`isPendingSection` 已经统一了四处口径。
