**⚠️ 表格行的坑（必须记住）**

真正数据行从**第 3 个**开始。第一轮探针按"前 2 行"取样时全空，就是这个原因。

### 2.2 发布（半自动）——**图片上传与类目选择的实测结论**

- **图片上传可控**：微信小店（3 个 file input）、拼多多（1 个）都是标准 `input[type=file]`，
  意味着 §7.3 里"图片自动上传"从"待实测"变成**可行** ✅
- **类目必须人工确认**：三个平台的类目分别是「下拉」（抖店）、「搜索式」（微信）、「独立页」（拼多多）——
  形态各异且都不可猜，**方案里"建议 + 人工确认"的判断被实测支持** ✅
- **回读可行**：三个平台发布页都是标准 `input`（`typeof value === 'string'`），
  §7.5 的"回读闭环"（越用越自动）**前提成立** ✅
- **抖店的发布是页内弹层**（URL 不变）→ `ProductProfile` 不能只靠 `publishUrl` 导航，
  必须支持"**点击入口 → 在弹层里操作**"这一形态

- 决定性证据：`artifacts/product-probe/pdd-goods-list.png` 截图里的 `19.99～29.99`、`8000`、`837429019978`
  与提取到的文本**逐字一致**。

> 结论：价格与库存**可以直接读文本**，不需要 OCR、不需要字体映射表。

## 5. M1 打样平台：**微信小店**

理由（全部来自实测）：

1. 商品列表是**标准 `<table>` + `<th>`**（6 列表头齐全），行文本完整可读 —— `readTable` + `headerMap` 直接可用；
2. 有 `共4条` 可作**条数核对基准**（M1 验收要用）；
3. 行内含**商品 ID**（`ID: 10001…`）→ `platform_platform_id` 有来源；
4. 与库中该店商品数（表里 `共4条`）一致，样本真实；
5. 发布页的图片上传与字段回读都已实测可用 → **M3 能顺着同一条路走通**。

次选：**拼多多**（19 个在售商品、ID 可读、状态页签计数，但列映射要绕开"无 `<th>`"）。

> 快手需要先补测商家后台的商品列表结构，再决定是否纳入 M1 铺开范围。

| 未实测平台（抖店 ×2 / 拼多多） | 全部返回 `DATA_SOURCE_NOT_VERIFIED`，主进程原话「…尚未实测到商品列表，暂不能同步」，**未写任何数据** |
| 微信小店同步 | 拉到 **4** 件、新增 4、页数 1、未截断；主进程原话「已同步 4 件（页面显示共 4 条）」 |
| **与页面条数核对** | 页面显示 `共4条`，库里 4 条 → **一致** |
| 再同步一次（幂等） | `inserted=0 / updated=0 / skipped=4` |
| `products.list`（只读商品页数据源） | 总数 4、返回 4，价格/库存/状态都有值（如 `2990` 分、库存 `60000`、`on_sale`） |

### 7.2 验收抓出来的三个真实缺陷（都已修 + 已加回归测试）

**① 把"登录态判不出来"当成了"未登录"**
微信小店的登录正向锚点是**经营数据**（成交金额…），只存在于后台**首页**；
店铺标签页停在**商品列表页**时 `detectStoreLoginStatus` 只能给 `UNKNOWN`。
而同步门禁原本写的是 `if (login.status !== 'LOGGED_IN') → LOGIN_REQUIRED`，
于是页面上明明摆着 4 个商品，却报「该店铺未登录」。
→ 修正：只拦**明确的否定证据**（`LOGIN_REQUIRED` / `VERIFY_REQUIRED`）；`UNKNOWN` 继续采集，
并在采集失败时把"也可能是会话过期"这条线索一并说给用户。这与 STORE_STATUS 那条修复同一个道理：
**未知证据不得当作否定证据**。回归测试：`product-sync-service.test.ts` 两条。

**② 就绪判据太早："标题对了"不等于"能读了"**
`urlMarker`（「商品列表」）**就是页面标题**，SPA 一换标题就命中，而表格要晚才渲染 →
读到空表，被误报成「平台改版」。
→ 修正：`waitForProductListReady` 现在要求**表格已可见**才算就绪。

**③ 表格比数据行先渲染**
拿到"表格可见"之后 `tbody` 仍可能 0 行 → 刚打开店铺就同步会得到「已同步 0 件」。
→ 修正：0 行时重试（6 次 × 1.2s）。

### 7.3 这一轮修出来的两个落库 bug（单测抓到，不是真机抓的）

- **新插入的行会被自己标成 `missing`**：`seenIds` 只收集"已存在"的行 id，
  首次同步时它是空的 → 同一个事务里的"标 missing"语句把刚插进去的商品全标成 missing。
- **"没变"被误判成"变了"**：`raw_snapshot_json` 存的是整行原文，却拿它跟字段指纹比较 →
  永远不等 → 每轮全量 UPDATE。现在存 `{ f: 指纹, r: 原文 }`：比较用 `f`，排障用 `r`。

> 这三条缺陷没有一条是"看代码看出来的"，都是**跑了真机/写了断言之后才暴露**的。
> 这正是方案 §14 把"真机验收"写进 DoD 的理由。

### 8.1 铺开过程中抓到的 4 个真实缺陷（都已修 + 有回归测试）

**① 选表按"表头最多"→ 选中了空表**（快手/拼多多实测：表头表与数据表是**两张表**）

**③ 只判"0 行"挡不住"1 行假数据"**

判据用页面自己给的数字，比任何启发式都可靠。

旧读取器碰巧抵消了这个错，改成新读取器后立刻暴露：4 个商品全被解析成"没有 ID"。
→ 档案按实测改成 `false`；同时**把偏移限定为只对 `index` 策略生效**（header 策略靠表头文案定位列，
本来就不该吃偏移），避免同一类错误再犯。

**⑤ 复活失效**：标 missing 时只改了 `platform_status`、没改指纹，于是下一轮"指纹相同 → 跳过"，
状态永远卡在 missing。
→ 状态与指纹**任一变化**都要写库。验收里已看到微信那 3 条从 `missing` 复活为 `on_sale` / `off_shelf`。

### 11.2 两个必须记住的坑

**① 发布页会被平台的"继续编辑"状态劫持（危险）**
在**旧标签页**里导航到 `https://store.weixin.qq.com/shop/goods/entry`（新增商品），
最终 URL 会变成 `…/entry?productId=<上一个编辑过的商品>` —— **用户以为在新建，其实在改既有商品**。

→ 修法：发布页**必须在新标签页里打开**（新标签页没有那个编辑状态）。实测有效：
新标签页里最终 URL 就是 `…/shop/goods/entry`（**没有** productId）。

**② "到位"判据不能只比 origin+pathname**
新增商品页与"既有商品编辑页"的 **pathname 完全相同**（都是 `/shop/goods/entry`），
只比 pathname 会把"停在别的商品的编辑页"判成"已打开发布页"（实测踩到，报了个假阳性）。

→ 修法：除 origin+pathname 外，**最终 URL 不允许出现目标 URL 里没有的 query 键**
（新增商品的目标 URL 没有 query，一出现 `productId` 就说明不是新增页）。
平台跟踪参数会让"其实到位了"被判成"没到位"——这个方向是**安全**的（fail-closed）。
未到位时如实说"这是既有商品的编辑页（多了 productId）"，并**绝不在错误页面上代填**。

### 11.3 人工边界的落点

- IPC 只有 `products:publish:preflight`（只算不写平台）、`products:publish:open`（只把页面开到发布页）、
  `products:publish:items`（只读台账）——**没有任何一个能让应用替你点提交**；
- 台账 `product_publish_jobs.mode` 的 CHECK 约束只有 `'fill'` 一个值，把"不可配置的人工边界"落到 schema 上；
- 实测确认：打开发布页后 `商品名称` 输入框仍为**空**（未代填任何内容）。

### 11.4 L1 代填实测（2026-09-30）

`fill=true` 时代填实测过锚点的字段，**每个字段写后回读**：

| 字段 | 结果 | 说明 |
| --- | --- | --- |
| 标题 | ✅ 写入=回读=本地标题 | 锚点 `placeholder 含「商品名称」` |
| 价格 | ⛔ 如实报"页面上还没有这个字段" | **新增商品页要先有「规格」才出现价格/库存区块** |
| 库存 | ⛔ 同上 | 那两个锚点是在**编辑既有商品**页上实测的 |

**又一个坑：发布表单整页在 ShadowRoot 里。**
代填第一版用普通 `document.querySelectorAll('input')`，**一个字段都找不到**，
表现为"等了 31 秒表单始终没渲染出来"——白排查了一轮。
详情页读取器一直用的是穿透版 `__roots()`，所以它能读到；代填这边漏了。
→ 修法：代填的注入脚本统一用穿透 ShadowRoot 的查询（`__inputs()`）。

**另一个坑：不要把消息拼进注入脚本。**
把"原因说明"用模板字符串 + `JSON.stringify` 拼在注入脚本内部，极易写出语法错误，
而注入脚本的报错只会给一句 `Script failed to execute`，很难查（实测踩到两次）。
→ 修法：注入脚本只返回**原因码**（如 `NOT_FOUND`），消息在 TypeScript 侧拼。

**URL 到位 ≠ DOM 就绪。** 新标签页刚打开时 URL 已经对了，但表单还没渲染（`input` 数为 0）。
→ 修法：填之前先 `waitForPublishForm`（按"实测锚点里至少出现一个"轮询，默认 30 秒），
等不到就如实说"一个字段都没填"，不硬填。

### 11.5 ⚠️ 锚点必须标明"在哪个页面测到的"（2026-09-30 更正）

**新增商品页与编辑既有商品页共用一个 URL**（`/shop/goods/entry`，编辑页多带 `productId`），
但**渲染出来的字段不一样**：

| 字段 | 新增商品页 | 编辑既有商品页 |
| --- | --- | --- |
| 标题 | ✅ 有（**实测代填成功**：写入=回读） | ✅ 有 |
| 短标题 / 品牌 / 类目 / 价格 / 库存 / 图片 | ❌ 实测**没有**这些字段 | ✅ 有 |

所以发布档案里每条锚点都加了 `pageScope`（`new` / `edit` / `new+edit`），预检据此决定
"这一项能不能在新增页上代填"：**在编辑页测到的锚点，不能在新增页上承诺代填**
（那只会得到"页面上还没有这个字段"）。本地有值却填不了的，给 **warning** 并说明原因。

顺带修掉两个**我自己猜出来的**错误：

1. 预检曾把微信的**副标题**标成"该平台不支持"——那是**没实测就下的结论**。
   实测发布页明明有 `请输入商品短标题`。**猜出来的"不支持"比"不知道"更糟**：
   它会让一个能填的字段被静默丢掉。
2. 预检曾对「规格」说 `fill`，但档案里**根本没登记 spec 的锚点** —— 说了要填却不会填。
   → 规则改成：**档案里没登记的字段 = 没实测过 → 一律不代填**，并如实写"尚未实测到锚点"。

**顺带一条纪律**：注入脚本只返回**原因码**，消息在 TypeScript 侧拼；
模板字符串 + `JSON.stringify` 混着写极易出语法错误，而注入脚本的报错只有一句
`Script failed to execute`，很难查（本轮因此踩了三次）。

### 11.6 回读校验：**必须对基线比对**（2026-09-30 实测踩到的假阳性）

第一版回读的判据是"**这个标题在不在本地台账里**"——对一个**本来就同步过**的商品，
它直接报了 `confirmed`。也就是说：**用户根本没提交成功，应用也会显示"已确认"**。
假阳性比不校验更糟，因为它会让人相信一件没发生的事。

**正确口径**（`evaluateReadback`，纯函数 + 单测）：

1. 开人工门禁时记下**基线**：那一刻该店已知的平台商品 ID 集合；
2. 回读时**先做一次只读同步**去平台上回查（只查本地台账会拿到过时数据）；
3. 只认**基线之后新增**的记录：
   - 新增里标题恰好匹配 1 条 → `confirmed`
   - 新增里 0 条匹配 → `needs_review`（可能还没同步，或提交没成功）
   - 新增里 ≥2 条匹配 → `needs_review` + **疑似重复提交**（§7.7）

**真机验证（什么都没发布）**：

```
开门禁：ok=true runId=run_63dd…
「我已提交」：state=verifying
只读回读：state=needs_review matched=0
回读原话：回读没有找到任何新增记录 —— 可能还没同步过来（先跑一次商品同步再看），或提交其实没成功
         （已回查平台：拉到 4 条）
```

修这个 bug 的过程中还牵出一个**台账写入**的问题：`confirmSubmitted` 更新状态时没带 `evidence`，
把 `openHumanGate` 记的基线**覆盖成了 NULL**（回读于是又把一切当成"新增"）。
→ 修法：台账更新时 **`evidence` 没传就保留、传了就浅合并** —— 台账是"一路记下来"的东西，
后一步不该把前一步的证据抹掉。

### 12.7 会影响实现的坑（**共 5 条，每条都是实测踩出来的**）

- **按钮禁用不体现在 `disabled` 属性上**：截图里「下一步」明显是灰的，而 `el.disabled === false`。
  判断可点性要读**样式类名**（如 `weui-desktop-btn_disabled`）。
- **发布页有「未保存离开」确认守卫**（按钮 `取消` / `确定离开`）。
  以后关闭发布标签页、或批量流程切换商品时**必须先处理它**，否则可能卡住或误丢表单。
- **坐标在视口外时点击静默无效**：`getBoundingClientRect()` 返回的是**相对视口**的坐标，
  元素在屏幕外时它是越界的（实测 `y=863` 而视口只有 704px）。
  而 `Input.dispatchMouseEvent` 只往视口内投递——**点在视口外等于没点，且不报错**。
  → 点之前先 `el.scrollIntoView({ block: 'center' })`，**重新读坐标**，并确认落在视口内。
- **模态弹窗的遮罩会吞掉所有点击**：弹窗开着时，背后页面的元素**找得到、坐标也对**，
  但点上去毫无反应（点的是遮罩层）。→ 动任何元素前先确认没有弹窗挡着。
- **⚠️ 任何 DOM 读取都必须穿透 ShadowRoot，否则"空结果"是假的**。
  微信整页在 ShadowRoot 里，而下面这些 API **都不穿透**：
  `document.querySelectorAll`、`DOM.querySelectorAll`、`document.body.innerText`。
  本项目**为此栽过三次**：

  | 症状 | 真相 |
  | --- | --- |
  | `DOM.querySelectorAll('input[type=file]')` 返回 0 个 | 元素在 ShadowRoot 里，不是不存在 |
  | 等了 31 秒"表单还没渲染" | `document.querySelectorAll('input')` 查不到 ShadowRoot 内的输入框 |
  | 判断"弹窗已关"（`body.innerText.includes(标题)` 返回 false），截图里弹窗明明开着 | `innerText` 读不到 ShadowRoot 内容 → 误判 → 去点背后的下拉 → 点在遮罩上 |

  **共同点：都"看起来查了"，但结果为空，且不报错。**
  → 正确姿势：遍历 `document.querySelectorAll('*')` 收集 `el.shadowRoot`，
  再在每个 root 上查询；读文本也一样要拼各 root 的 `textContent`。
  判断"到底有没有"**只能靠截图**——这是本项目里唯一可靠的兜底手段。

#### 12.9.3 最终阻塞：微信小店的登录检测不触发（**不在商品模块范围内**）

三处都修完后回读仍失败，原因是**店铺状态**：

```
① 前置：打开微信小店（当前 offline）
   +3s/+18s/+33s/+48s/+63s/+78s 状态=offline
   ❌ 90 秒内没变 online
```

而主进程日志里，登录检测**只在快手小店上反复跑**（没有一条是微信小店的）。

**连锁影响**（一个根因，三个现象）：

| 现象 | 说明 |
| --- | --- |
| 微信小店一直 `offline` | 登录检测没触发 |
| 微信小店「同步失败」 | 同上 |
| 预检/回读落到别的店（快手/拼多多） | 界面「发布预检」只取 `status === "online"` 的店铺 → **offline 的店根本不进目标列表** → 落到列表第一家 |

> ⚠️ 容易忽略的点：`offline` 的语义是"**窗口没开 / 还没确认登录**"（见 12.7），
> 而「发布预检」按 `online` 过滤目标店铺 —— 两者叠加的效果是：
> **店铺窗口没开时，它的商品会被拿去别的店铺预检**，用户看到的是"它去读了一家我没要发的店"。

**这一条属于 `platform-login-service` / 平台适配器那一层**，不在商品模块范围内。
本模块的结论到此为止：**回读代码本身的三处问题已修完，剩下的阻塞是店铺状态。**

#### 12.9.4 顺带验证：状态词表修复是对的

台账里真实存在 `filling × 21`（`awaiting_human × 49、confirmed × 2、filling × 21、needs_review × 1、pending × 3、precheck_failed × 13`）。
`filling` 正是 `IN_FLIGHT_PUBLISH_STATES` 里的四个"正在跑"状态之一 ——
证明"`in_progress` 是编的、真实名字是 `prechecking/filling/fill_partial/verifying`"这个判断是对的（见 §7.11）。

### 12.10 微信小店"永远 offline"的完整根因链（2026-10-02 查清）

这条链是本次排查最花时间的部分，**三层原因串成一条**，而且每一层单独看都不像问题。

#### 现象

微信小店的 `stores.status` 长期停在 `offline`，而「发布预检」只取 `status === "online"` 的店铺，于是：

- 微信小店的商品被拿去**别的店铺**（快手/拼多多）预检
- 回读也去读那家店 → 报"快手小店尚未实测到商品编辑页地址"
- ① 首次真实提交、④ 回读面板 DOM 实测都无法完成

等待窗口从 90 秒加到 180 秒、再到 635 秒（10.5 分钟），**都是 offline**。

#### 根因链（从下游往上游）

**第 3 层（最上游）：同步在店铺已有标签页里导航，被「未保存离开」守卫拦住**

实测：把店铺标签页导航到商品列表页 `https://store.weixin.qq.com/shop/goods/list`，
页面**没有变**——`location.href` 仍是 `/shop/goods/entry?productId=…`（商品编辑页）。

机制：那个标签页停在商品编辑页（且有未保存状态），平台的**「未保存离开」确认守卫**阻止了导航。
（这个守卫本模块早就记录过，见 12.7——但没想到它也会咬到**同步**。）

**第 2 层：`navigateTo` 的"导航被阻止"判据**从来没能生效**，于是把失败误报成成功**

```ts
// 原判据（错的）：比较"导航前"和"导航后"的 URL
if (urlBefore && urlNow && urlNow === urlBefore && urlBefore !== url) { … ERR_NAVIGATION_BLOCKED }
```

**实测（2026-10-02，靠一行诊断日志拿到的事实）**：

```
[navigate] ok target=…/shop/goods/list  before=（空）  now=…/goods/entry?productId=…
```

- **`before=` 是空的** —— `wc.getURL()` 在导航**前**读不到值（那时店铺标签页还没就绪），
  所以 `urlBefore && …` 这个前置条件**永远是假**，判据是**死代码**，导航被阻止也照样 `return { ok: true }`。
- `now=` 有值 —— 用**导航后**的 URL 和目标比 pathname 就行。

**修复后实测**：同步耗时从 **31 秒**（等一个永远不会就绪的页面）降到 **925 毫秒**，
错误码从误导性的 `PAGE_CHANGED / PAGE_NOT_READY`（"平台可能已改版"）变成 `NAVIGATION_FAILED`。

> 这一条的价值不在"修好了同步"（没修好），而在：**失败变快、变准，不再把用户指向"平台改版"**。
#### 一条链，解释了十几轮的现象

```
同步在旧标签页导航 /shop/goods/list
  → 「未保存离开」守卫阻止导航（ERR_ABORTED）
  → navigateTo 把它当"正常"吞掉，继续等 → 页面没变 → PAGE_NOT_READY（提示"平台可能已改版"是错的）
  → 标签页停在编辑页 → detectLoginStatus 给 UNKNOWN
  → UNKNOWN 不置 online → 店铺永远 offline
  → 预检只取 online 店铺 → 微信小店的商品被拿去快手/拼多多预检
  → 回读去读快手 → ④ 与 ① 全卡住
```

**也解释了为什么快手/拼多多一直 online**：它们的列表页没有这个守卫。

#### 另外两个独立确认的事实

1. **会话没有过期** —— 实测微信小店的页面能正常渲染，`title` = "微信小店 商品编辑"。
   所以 `PAGE_NOT_READY` 与登录无关。
2. **`openStoreBrowser(storeId, { display: false })` 会让页面不加载** ——
   实测同一个同步：`display:false` 时 **28 毫秒**就返回 `NAVIGATION_FAILED`（根本没尝试导航）；
   改成 `display:true` 后变成 **31 秒**真导航（然后才暴露上面那条守卫问题）。
   → 需要真实导航的路径要么显示打开，要么改成"隐藏也等 `did-finish-load`"。

#### 建议的修法（按优先级）

1. **同步也开新标签页**（照 `openForHuman` 的写法）——新标签页没有那个编辑状态，守卫不会触发。
   落点在 `sales-metrics-dom-adapter.ts` / `sales-metrics-page-reader.ts`（**所有平台共用**，改动影响面大）。
2. **`navigateTo` 不要无条件吞 `ERR_ABORTED`** —— 导航后校验最终 URL，没变就如实报"导航被阻止"。
   否则下次同类问题还是查不出来（这一条比第 1 条更重要：它保的是**可排查性**）。

#### 12.10.5 最终根因与修复（2026-10-02 晚）

**根因：`openStoreBrowser(storeId, { display: false })` 会让新标签页的 webContents 不被实例化。**

完整链条：

```
店铺浏览器以 display:false（不显示）打开
  → createTab 建出的新标签页**拿不到 webContents**（实测轮询 12 秒仍是 null）
  → 采集只能**退回店铺已有标签页**（那个标签页正停在商品编辑页）
  → 导航到 /shop/goods/list 落不到列表页
  → 登录检测给 UNKNOWN（登录锚点不在编辑页）→ 店铺**永远 offline**
  → 预检只取 online 店铺 → 商品被拿去别的店铺预检 → 回读也去读那家店
```

**一个根因（打开方式）同时造成了三个症状**，而我前面一直在修**下游**（导航、等就绪、异常日志）。

**修复：两处必须同时改，缺一不可**（这一点是实测出来的）：

| 改动 | 单独生效吗 | 实测结果 |
| --- | --- | --- |
| 开新标签页采集（避开编辑页） | ❌ | 窗口隐藏时标签页建不出来 → 退回 |
| `display: false` → `true` | ❌ | 没有新标签页时仍 31 秒超时 |
| **两个一起** | ✅ | **同步 SUCCEEDED、4 秒、店铺变 online、webview 停在商品列表页** |

同一个修法也修好了**回读**（`product-publish-service.ts` 的 runtime 同样是 `display:false`）：

```
回读: "回读到 3 项需要你决定（1 项建议存为默认值、1 项与本地不一致）—— 应用不会自动改"
```

> ⚠️ 取舍：`display: true` 会让同步时**弹出店铺浏览器窗口（抢焦点）**。这是让新标签页能实例化的
> **必要条件**（实测）。若要保住"不抢焦点"，需要另找办法让隐藏窗口下的标签页也能实例化。

#### 12.10.6 已修：回读面板从不渲染（根因：视图切换卸载组件 + watch 停止）**（2026-10-02 修复）**
**✅ 修复（2026-10-02）**：在 `runReadback` 里**直接写模块级缓存**，不依赖 `watch`：

```ts
readback.value = { itemId, suggestions, readFields, missingFields }
readbackCache.current = readback.value   // ← 直接写；组件已卸载也照样写
```

**真机验证（前置：店铺 online）**：

```
C 回读期间的 toast: ["回读到 3 项需要你决定（1 项建议存为默认值、1 项与本地不一致）"]
D 现在所在页: 店铺工作台
E 回商品管理后: {"dbg值":"有值:4", "面板":true, "建议行":6}     ← 面板出现了
```

**最终根因链（完整）**：

```
点「回读页面实际值」
  → 回读要打开店铺页面 → 应用切到「店铺工作台」→ UnifiedAppsPage **卸载**
      （Vue 卸载时会**停止该组件的所有 watch**）
  → IPC 稍后 resolve → readback.value = {...}  发生在**已卸载**的组件上
  → ws.toast(...) 是全局的，照样显示          ← 所以看到"成功"
  → 而 watch 已经死了 → **缓存永远为空** → 回到商品管理时 readback 又是 null
```

> **这个 bug 教了两件事**：
> 1. **不要把"结果要跨视图存活"的状态交给 `watch` 同步** —— 组件卸载后 watch 就停了，
>    而**异步任务在卸载之后才完成**是常态。直接写在赋值处。
> 2. 排查时**先测那条能区分多种可能的中间事实**（这里就是"回读成功了吗 + 缓存有值吗"）。
>    我在这两种可能之间猜了 4 轮、每轮跑 4 分钟；**一次测量就定论**。

**现象**：回读**功能成功**（toast 打出"回读到 3 项需要你决定…"），但**面板从不出现**。

**实测证据**（从点击那一刻起每 500ms 查一次，连续 30 秒）：

```
+5.0s  {"面板":false, "toast":"回读到 3 项需要你决定（1 项建议存为默认值、1 项与本地不一致）…"}
+10.0s {"面板":false}   …   +30.0s {"面板":false}
```

**已排除**（都做过实测或代码核对）：

- ❌ "查得太晚" —— 每 500ms 查了 30 秒
- ❌ "父容器没挂载" —— 面板（L247 `v-if="readback"`）与预检面板（L128 `v-if="preflight"`）是**同级兄弟**，
  而预检面板明确在渲染（否则它内部的回读按钮点不到）
- ❌ "`readback.value` 没被赋值" —— 成功 toast 就在赋值语句的下一行（`UnifiedAppsPage.vue` 的 `runReadback`）
- ❌ 作用域问题 —— 组件是 `<script setup lang="ts">`，ref 自动解包

**未排除的只剩一个**：模板里的 `readback` 不是那个被赋值的 ref。

**下一步（唯一能定论的测法）**：在浏览器控制台里**直接读活组件的状态**，而不是从 DOM 反推：

```js
const el = document.querySelector('[data-test="publish-preflight"]')
let c = el.__vueParentComponent
while (c && !('readback' in (c.setupState || {}))) c = c.parent
JSON.stringify({ 有值: !!c?.setupState?.readback, 建议数: c?.setupState?.readback?.suggestions?.length })
```

> **这个 bug 的性质值得强调**：它是 §7.11 定义的**静默失效**典型 ——
> **功能做完了、数据也读了、toast 还报了成功，但用户什么都看不到，而且不报错。**
> 排查时最容易走错的方向是"回读为什么失败"——真相是"回读成功但结果没显示"。

#### 12.10.7 这次排查最该记住的一条

这条链我错了**六次**（"会话过期"、"被守卫拦住"、"接口没有 getURL"、"我的检查触发了"、
"`navigateTo` 从未被调用"、"新标签页里也失败"）。**六次都是同一个错误**：

> **从下游现象反推上游状态，而不直接测量上游。**

真正的转折是**在 `navigateTo` 里加了一行日志**：

```

```

**一行日志定论了四个我猜错的疑点。** 对比之前"改条件 → 跑 4 分钟 → 看最终文案 → 猜错"的循环，
成本差了一个数量级。

**所以：改任何代码之前，先确认它会被执行（一行日志）；判断任何状态之前，先直接测量它。**

### 12.11 挡死主链路的真 bug：已链接的商品**永远发不出去**（2026-10-02 查明并**已修**，见 §12.11 末）

**这是「本地商品发布到指定店铺」这条主链路的致命伤**：一个商品只要在某家店发过一次，
**它就再也发不出去了**，而且界面还告诉用户"改了内容就能发"。

#### 现象

```
预检: verdict = blocked
blockers: [{
  level: "blocker", field: "title",
  message: "该店铺已经有这个商品的平台记录（平台商品 ID 10000616807249），且本地草稿与上次完全一致",
  fixHint: "要更新平台商品请用平台的编辑入口；**本地内容改了之后才会允许再次发布**"
}]
```

**实测：改了标题、`library.save` 成功、`draftHash` 变了 —— 预检仍然 blocked。**

#### 根因：判定条件与文案不一致，而比较所需的数据**根本没落库**

```ts
// packages/shared/src/product-publish-rules.ts:154
const sameStore = input.existingLinks.filter(link => link.storeId === target.storeId)
if (sameStore.length > 0) {          // ← **只判断"有没有链接"，没有任何内容比较**
  blockers.push({ … message: '…且本地草稿与上次完全一致', fixHint: '…本地内容改了之后才会允许再次发布' })
}
```

而数据模型里**没有"上次发布时的草稿指纹"**：

```ts
existingLinks: Array<{ storeId; platform; platformProductId; platformStatus }>   // ← 没有 hash
```

**所以不是"忘了写比较"，而是"比较所需的数据没有存"** —— 文案承诺了代码**无法实现**的条件。

按 §7.11 的分类，这属于**静默失效**的近亲：**文案描述了一个不存在的条件**。
用户照着提示改内容 → 界面还是拒绝 → **且不告诉真实原因**。

#### 修法（4 个文件，需要一致改动）

1. **迁移**：`product_platform_links` 加一列 `draft_hash TEXT`（nullable）。
   ⚠️ 迁移版本号**已被别的改动占到 v28**，新迁移从 **v29** 起（见 `migrations.ts`）。
2. **仓储**：发布成功（`confirm`）时，把当时的草稿 hash 写进这条链接。
3. **规则**（`precheckPublish` ③ 那段）：
   ```
   link.draftHash && link.draftHash === product.draftHash  →  blocked（确实是"白跑一趟"）
   否则                                                     →  放行（改过了，这是"更新"）
   老数据（draftHash 为 null）                              →  放行（不能因为缺数据就永久禁止发布）
   ```
4. **回归测试**（`tests/unit/product-publish-rules.test.ts`）：
   - 草稿 hash 相同 → **blocked**
   - 草稿 hash 不同 → **不 blocked**（**今天这条会失败**，因为现在是无条件 blocked）
   - 老数据 hash 为 null → 不 blocked

#### 为什么必须修

**它挡住了模块的核心功能。** 商品管理模块的全部价值就是"把本地商品发到指定店铺"，
而这条链路**在商品发过一次之后就断了**，并且**用一个假的理由骗用户**。

### 12.13 「关不掉的弹窗」（2026-10-02）

> ⚠️ **本节结论经后续实测更正，先看这里**：

#### 真相

**弹窗根本不在。** 两条独立证据：

1. `document.elementFromPoint(965, 72)` 返回的是**页面顶部 header**（"下载客户端/平台客服/客服/通知"），**不是弹窗**
2. 把判据换成可靠的 `elementFromPoint` + 祖先链比对后，`modalOpen()` **如实报「否」**

弹窗只在点「上架」后**极短的一瞬**出现（§12.12 的截图正好抓到），**工具 20 秒后才去处理，那时早就不在了**。
**而且"关掉它"并不是提交的必要步骤。**

#### 根因：判据永远返回同一个值

```js
// 第 1 版（错）：拼**所有** shadow 的 textContent 找文案
for (const r of roots()) text += ' ' + String(r.textContent || '')

                                               // → **永远报 open: true**

// 第 2 版（还是错）：加"可见性"检查
const vis = el => { const r = el.getBoundingClientRect(); return r.width > 0 && r.height > 0 }
                                               // **宽高非零 ≠ 用户看得见**：可被父级裁剪、被遮挡、在视口外

// 第 3 版（对）：问"这个点上用户真正能点到什么"
const top = document.elementFromPoint(cx, cy)
const covered = domPath(el).includes(top)      // domPath 跨 shadow 用 getRootNode().host 上溯
```

   一版在页面里抛异常）。**把"诊断没输出"当成"没有更多信息"是错的** —— 它更可能是**诊断坏了**。

   **注释里的反引号也会终止模板。**

**「关掉弹窗」不是首次真实提交的障碍，这条可以从清单上划掉。**
