## 本次更新（0.4.40）：自定义任务「表单放行、创建被拒」与错误码被吞

这一版修的是上一版开放自定义任务后暴露出来的一类问题，共同点是**用户看到的原因和真实原因对不上**。

### 1. 校验清单放行、点创建却被拒（四个独立成因）

自定义任务的校验清单分两处实现：渲染进程的表单校验和主进程的 Zod schema。两边各写一遍，就会漂移——**表单说没问题、创建时报 `TASK_INVALID_STEP`**，而报错只给一个笼统的码。实测能复现的全部堵上：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 第 31 步 | 清单全绿 → 创建被拒（`max(30)`） | 清单直接报「步骤最多 30 步（当前 31 步）」 |
| `wx.qq.com/page`（漏了协议头） | 清单全绿 → 创建被拒 | 清单报「必须是完整网址（以 http:// 或 https:// 开头）」 |
| `javascript:alert(1)` / `ftp://x` | 清单全绿 → 创建被拒 | 同上，用 WHATWG URL 解析判定，不是正则凑合 |
| 501 字符的选择器 | 输入框填得下 → 创建被拒 | 表单加 `maxLength`，清单报「最多 500 个字（当前 501 个）」 |
| `waitMs = 3.5` | 清单全绿 → 创建被拒（`.int()`） | 清单报「必须是整数」 |
| `within.climb = 7` | 清单全绿 → 创建被拒（`max(6)`） | 清单报「上溯层数必须是 0~6 的整数」 |

判据统一为**子集关系**：客户端放行的，主进程必须也放行。全部字段的长度上限、数值范围、整数要求、网址格式都从主进程 schema 反推过来，写进 `STEP_CATALOG` 的字段定义里，清单直接按同一份定义校验，不再有两套判据。

### 2. 创建成功后草稿没清空，下次新建像是"填好的"

创建成功只关了对话框，没清 `customSteps` / `customTaskName`。再点「新建任务」时上一条的步骤和任务名还在，一眼看去像是预设好的模板，一点就建出个重复任务。现在成功分支清空草稿；**取消不清**——那是"还没建"，草稿留着是有用的。

### 3. 五种错误码被吞成「内部错误」

`task-runner.ts` 里有个 `if` 链把异常映射成对外错误码，靠人工记得同步。它漏了 5 个码，于是这些失败在任务列表里一律显示 `INTERNAL_ERROR`：

- `TASK_TEXT_PRESENT` —— 页面出现平台给的失败文案（如快手「部分邀约发送失败」）。这是**业务结果**，报成内部错误会让人以为软件坏了，甚至去重发。
- `TASK_TARGET_COVERED` —— 目标被浮层盖住，把窗口拉宽就能解决。
- `CAPTURE_EMPTY` —— 截图时窗口没在合成，得让用户知道是"窗口没显示"。
- `TASK_INVALID_STEP` —— 步骤参数非法。
- `TASK_BAD_STATE` —— 状态机不允许的操作。

改法不是把那 5 个补进白名单（下次还会漏），而是抽成独立的 `error-classifier.ts`，两段式识别：已知码优先（保持 loop 的 `stopOn` / `onCode` 语义一字不变），再加通用兜底，认得形如 `CODE: 说明` 的错误码。其中还有一类白名单**永远扫不到**——`requireTextAbsent` / `requireQuota` 的 `code` 字段由用户在编排里填，是运行期才出现的自定义码，只有兜底能救。

兜底的两处收紧是为了避免误命中：要求码里至少含一个下划线（避开 `HTTP:` 这类噪音），且只认消息开头或冒号后的位置。这不是学术风险——loop 的 `stopOn` 会把命中的码当成"按预期收工"，误命中等于**静默漏发却记成功**。

配套单测会从 `task-runner.ts` 源码里扫出所有抛出的错误码，逐个断言分类器认识；以后新加错误码忘了登记会当场测试失败，而不是等用户看到"内部错误"。

### 4. 旧数据库缺任务查询索引（迁移漏做）

`idx_task_runs_status` 和 `idx_task_step_results_run_step` 只写在 v1 建表迁移里。**老库不会重跑 v1**，所以 0.4.39 之前建的库一直缺这两个索引（全新安装的库有）。新增 v4 迁移用 `IF NOT EXISTS` 补上，兼容两种情况。任务一多，任务列表按状态查询和步骤结果按 `(run_id, step_index)` 取数都会走这两个索引。

### 一并带上的邀约性能与稳定性调整

- **主窗口崩溃恢复加 24 小时绝对上限（10 次）**：原来只有"5 分钟内最多 3 次"的滑动窗口，在窗口边界反复重置计数器即可绕开，理论上仍能陷入崩溃-重载循环。
- **AI 话术生成超时 90s → 120s**：真机实测第 25 轮 `aiGenerate` 超时会把整批（前面可能已真实发出 20 多位）打掉，模型一次推理慢不该让整批作废。
- **批量勾选滚动**：滚动步长改为动态（距离底部远时 1.2 屏、接近底部收敛回 0.95 屏），落定检测由 20×80ms 改为 10×100ms，省掉约 0.8 秒/轮。

### 验收

- 单测 **277/277 通过**（新增 `error-classifier.test.ts` 7 条、`migrations.test.ts` 6 条；`custom-task.test.ts` 扩到 39 条）
- `tools/acceptance/custom-task-local-verify.js` **43/43 通过**（新增第 ⑧ 段真实执行验证：读值、点击落页、截图落盘哈希一致、5 步结果逐条落库、预期失败任务的 `errorCode` 确为 `TASK_TEXT_PRESENT`）

### 未验证边界（如实标注）

## 本次更新（0.4.39）：步骤目录加筛选——修「找不到某一步」

上一版的三栏布局有个我自己引入的缺陷，被使用反馈直接命中：**问「点击元素怎么添加到新建任务」**。

量了一下才看清问题：左栏目录共 22 项、分 6 组，栏内可视高度只装得下 10 项（内容 748px / 可视 356px），而**「点击元素」在折叠线以下**（y=736，栏底 690）——而且栏内没有任何提示说明还能往下滚。用户看到的是一份"没有点击元素"的目录。

修法：

- **左栏顶部加筛选框**：输「点击」只剩「点击元素 / 按文案点击」两项，且全部落在视野内、无需滚动。这是"找不到某一步"的标准解法，任何窗口高度下都成立，不再依赖"恰好滚到了那一屏"。
- 筛选同时匹配**分组名**（输「交互」会把整组带出来）与英文 type。
- 表头显示**条目总数**（`22 项`），暗示还有内容在下面。
- 条目压紧 + 左栏由 156px 加宽到 176px（「切到已打开的标签页」9 个字在 156px 下会折行）。

### 怎么添加一个步骤（顺带说明）

新建任务 → **任务类型选「自定义任务」**（默认的「达人邀约」是已封装流程，里面没有步骤编辑器）→ 左栏找或筛选步骤、**点一下即添加** → 右栏填参数。若这一步是"发出后不可撤销"的提交动作，勾上「提交动作」，系统会要求它前面有一道人工确认门禁。

## 0.4.38：自定义任务改成三栏布局（目录 / 序列 / 参数）

0.4.37 的自定义任务编排器是单列纵向堆叠，加步骤、排顺序、改参数三件事挤在一起：步骤一多就要滚动，改中间某一步的参数得先滚到它，加步骤还要点开下拉再找（真机验收时那个下拉弹层就点偏过两次）。

拆成三栏后，三件事各占一块、互不遮挡：

- **左栏 步骤目录**：按用途分组常驻，点即添加；
- **中栏 已编排序列**：看全局顺序，每行显示该步最关键的那个参数（如 `url:` / `text:`），不点开也认得出是哪一步；上移/下移/删除在这一行上；
- **右栏 参数**：只渲染**选中那一步**的表单，加上"提交动作"勾选。

### 顺带修掉一个会让人找不到原因的可用性坑

三栏改完我量了实际尺寸，发现对话框内容高 887px 而可视区只有 718px——**「创建任务」按钮和校验清单被一起推到视野外**。校验清单正是"为什么按钮是灰的"的解释，它看不见，用户就只看到按钮点不动、不知道去哪儿改。这是从单列改三栏时最容易丢掉的可用性。

改法：这一档对话框不再沿用 `.modal` 的"固定 80vh + 整体内滚动"，而是 flex 列布局——标题/任务类型/任务名/定时/按钮都是固定项，只让中间的编排器滚动。实测修好后 `actionsVisible: true`、`footVisible: true`、内容高度与可视高度一致（不再溢出）。

另外把**校验清单固定为右栏页脚**（不随参数滚动），同样是为了保证"为什么不能创建"始终可见。

### 验收

`tools/acceptance/custom-task-local-verify.js` **23/23 通过**（脚本已改用左栏目录点选，不再走下拉开合）。三栏下左栏渲染的 22 个步骤类型仍只有安全那些——`loop` / `ensureRows*` / `aiGenerate` 等高风险步骤不在目录里。

## 0.4.37：新建任务支持「自定义任务」——可视化步骤编排（带创建前校验）

「新建任务」此前**刻意只从已实测跑通的流程里挑**，不给底层步骤编辑器。理由是明确的：引擎步骤类型有 20 多种，让用户自己拼 `navigate` / `readTable` / `click`… 必然拼出跑不通的半成品（选择器写不对、少了必要的等待、提交类动作漏了确认门禁），而失败会以"任务失败"的形式回抛，用户无从对应到"我少填了哪个字段"。

这一版按需求开放了这个能力。**但不是把那条理由无视掉，而是把它逐条堵上**——否则就是明知故犯地造一个产出坏任务的功能：

| 当初的顾虑 | 这一版怎么堵 |
|---|---|
| 选择器写不对、字段拼错 | 不再让用户裸写 JSON，而是**按目录渲染表单**：每种步骤只暴露引擎真正接受的字段 |
| 少了必要的等待 | 步骤按用途分组（导航/等待/读取/交互/断言/门禁），并对"开局没有导航"这类疏漏给警告 |
| 提交类动作漏了确认门禁 | 副作用步骤要求用户**显式标记"提交动作"**，校验强制它前面必须有 `waitForUserConfirmation`，缺失直接拒绝创建 |

### 关键设计：判断归用户，约束归系统

同一个"按文案点击"，点「搜索」和点「确认发送」的危险程度天差地别，而步骤类型看不出区别。所以"这一步是不是不可撤销的提交"由**用户标记**（把判断放在知道业务的人手里），但一旦标了，系统就**强制**它前面必须有一道人工确认门禁——且门禁放在提交动作**之后**不算数，顺序必须对。缺失时创建按钮置灰，并写明原因：

> 第 2 步「按文案点击」标了"提交动作"，但它前面没有人工确认门禁——请在它之前加一道「人工确认门禁」，否则任务会在无人值守时直接发出不可撤销的操作

### 收录口径：哪些步骤给了，哪些刻意没给

给了 20 种可独立表达的步骤（打开网址、切标签页、等页面/元素/文案/消失、固定等待、读取文本/按标签读值/读表格、截图、点击元素、按文案点击、有就点没有就跳过、批量勾选、填写输入框、键盘输入、按键、断言数字/按钮可用/文案不出现、人工确认门禁）。

**刻意没给**（不是漏了）：`loop` / `onCode`（嵌套编排需要另一套递归 UI，且它承载的是"批量发送"这类高风险流程）、`ensureRows*` / `aiGenerate` / `mirrorTabUrl` / `fillDraft`（平台流程专用，脱离该流程没有意义）。这些仍由各自的业务面板按已实测档案创建。

### 防漂移：目录与引擎 schema 必须一致

编排器按目录渲染表单、按目录裁剪字段，而**权威校验在主进程的 Zod**（`strict()`：多一个键、少一个必填都会整单被拒）。两者一旦不一致，用户就会"表单填得好好的、点创建被拒"，且错误信息是引擎味的 `TASK_INVALID_STEP`——正是当初决定不给步骤编辑器的理由。

所以用单测把一致性钉死：按目录填出的样本必须能通过主进程的 Zod；数值范围与 Zod 对齐（含"超出目录声明的上限必须也被 Zod 拒"这条反向断言）；目录里每种步骤都必须在引擎白名单内。**29 个单测**覆盖这些契约。

### 验收

新增 `tools/acceptance/custom-task-local-verify.js`（CDP 驱动真实渲染层 + 独立临时 userData，不碰真实数据），**23/23 通过**。为什么用 CDP 而不是像素点击：本功能是"表单 + 小按钮"的界面，像素坐标在缩放/滚动下极易点偏，而验收要断言的是**行为**（门禁拦不拦、创建出来的步骤对不对），不是"我点没点中"。覆盖：选项存在且未被误标"不可用"、空编排置灰、加步骤/排序、**标记提交动作但无门禁 → 拦下**、门禁放在后面仍被拦、补门禁后恢复、创建成功且落库步骤与编排一致、编排器元数据（`submit`）不混进引擎步骤、高风险步骤不在目录里。

### 其他

- 编排中的步骤草稿在对话框关闭后保留，不会因为误点遮罩而白填一遍。
- 自定义任务的阻断原因按"最该先解决的那一个"给；明细在编辑器下方逐条列出（错误红字、警告黄字）。

## 0.4.36：店铺页面右键「元素定位信息」——取选择器不用再开 DevTools

任务引擎的每一步都依赖档案里的**选择器与文案锚点**（`packages/shared/src/constants/*`），而这些常量只能靠真机实测得来：平台类名普遍带构建哈希，写死等于猜测。此前取一个锚点要开 DevTools 手动翻 DOM，这一版把它变成一次右键。

### 怎么用

在店铺页面任意元素上右键 → 「**元素定位信息（供任务步骤取选择器）**」：

- 页面上该元素被**蓝框高亮 2.5 秒**（并标注标签与文案）——页面里到处是透明包裹层，不框出来无法确认工具选中的是哪一层；
- 整理好的锚点**直接进系统剪贴板**，可粘进档案常量文件；
- 同时留一条日志（含完整原始数据），剪贴板被覆盖后仍可追溯。

### 采集什么：按"平台改版后的存活率"分三层给出

| 层 | 内容 | 引擎里对应的写法 |
|---|---|---|
| 1. 文案锚点（最稳） | 元素的**自有文本** | `clickByText: { text: "..." }` |
| 2. 稳定属性（次选） | `data-*` / `name` / `aria-label` / `placeholder` 等 | `waitForSelector: { selector: '[data-test="..."]' }` |
| 3. CSS 路径（最后手段） | 带 `:nth-of-type` 的路径 | 兜底 |

另外给出「所在行」的定位范围（表格行/列表项）供 `within` 使用，并在元素位于 ShadowRoot 内时提示**需要加 `deep: true`**（微信小店的页面在 micro-app 的 ShadowRoot 里，不加取不到）。

### 真机实测修正：Tailwind 类名不是构建哈希

首轮真机实测（微信小店资质管理页）就暴露了一个会毁掉这个功能可信度的误报：`h-[44px]` / `pl-[28px]` 这类 **Tailwind 原子类名**含数字与方括号，被最初的"含数字即哈希"规则全判成了构建哈希。

误报的代价不是"多提示一句"，而是**警告整体失去可信度**——用户连着看几次假警报后，真正危险的 `css-1x2y3z` 也不会被当回事。修正后只认真正的随机标识特征，并把三类分开报：

- **疑似构建哈希**（`css-1x2y3z` / `btn_a1b2c3` / 超长无分隔符串）→ 明确警告"不要写进选择器"；
- **含 `[] : /` 需转义的类名**（`h-[44px]`）→ 提示"可用但要转义"，与"别用"是两回事；
- **语义化类名**（`flex` / `items-center`）→ 列为可用。

判定规则本身有单测直接跑（从注入脚本里抠出函数执行），不靠格式化层间接验证——因为误报的根因在判定规则里。

### 其他

- 菜单项在**独立窗口**里同样可用（独立窗口也要取锚点）。
- 无落点坐标时（键盘唤出菜单）该项**置灰而非隐藏**：让用户知道"重新右键即可"，比菜单项时有时无更好懂。用过期坐标采到的是**别的元素**，比不采集更误导人。
- 采集**全程只读**：除高亮遮罩外不点击、不派发事件，不改变平台任何状态。

## 上一版（0.4.34）：发票中心按店铺营业执照（开票主体）分账与筛选

发票是**按开票主体**开的，不是按平台账号开的。同一个营业执照下常常挂好几家店（同公司开了抖店 + 快手 + 微信小店），只看"店铺"就会把一个主体的票拆成几份、对不上账。这版给店铺加上**营业执照**这一维，并让发票中心能按它筛选。

### 筛选条：一点即筛，直接看到"这个主体欠多少票"

发票中心总览下方新增一条主体筛选条，每个主体一枚胶囊，**直接写着**「N 家 · M 条 · ¥金额」：

```
营业执照  [全部 4 家 · 54 条 · ¥4,966.67]  [上海某某贸易有限公司 3 家 · 12 条 · ¥431.85]  [未填写营业执照 1 家 · 1 条 · ¥1.00]
```

- 点主体胶囊 → 只留该主体的店铺，**上方的待开票条数 / 可开金额合计同步变成该主体自己的数**（这就是"给这家公司开票要开多少"的答案）；再点一下取消。
- 每枚胶囊上的金额都与"全部"口径一致：解析不出数字的不计金额但**照数条数**，也不受当前筛选影响（否则点一个主体，别的全变 0，没法横向比）。

### 归组口径（这是最容易出错、也最要紧的一段）

- **代码优先**：填了统一社会信用代码就按代码归组（名称写法不同、中间带空格、大小写不同都能归到一起）。落库前统一**去空格/连字符并转大写**——用户是从执照上连格式一起复制过来的。
- **只有名称的店**：若与某个有代码的主体**同名**，并进那个主体（用户常是先填名称、后来才补代码；不并会出现两个同名胶囊各 1 家，看起来像坏了）。
- **名称相近但不是同一家的绝不合并**（"上海某某贸易有限公司" ≠ "…分公司"）：错一个公司就是开错票。
- 位数不对的信用代码会被**拒绝并说明原因**（18 位，旧税号 15 位），而不是存进去另起一个主体；校验失败时**不关闭编辑框、不改本地数据**，界面直接显示主进程给的字段级错误。
- "一个主体有几家店"是按**整份店铺列表**算出来的（有的店没填代码、但它和有代码的那家同名），所以界面筛选用的是一张统一的归属表：胶囊写"3 家"，点下去就必须筛出 3 家，自相矛盾在实现层面被排除。

### 导出与存储

- **CSV 导出新增「营业执照 / 统一社会信用代码」两列**（排在店铺/平台之后）：导出的表是拿去报税、交给代账的，代账按主体分账，光有店铺名他们得再问一遍哪家店属于哪个公司。没填的写「未填写」而不是留空（留空和"漏导出"看不出区别）。

「重新加载」与「强制重新加载」**并排**给出：平台后台常把静态资源/接口响应缓存住（换了账号、
改了配置还是旧页面），这时只有忽略缓存的重载能救，不用再去手动清缓存。

### 为什么用原生菜单，而不是渲染层画一个

店铺页面是原生 `WebContentsView`，在窗口内容区里**永远画在渲染层 HTML 之上**。
渲染层自绘的菜单只有两条路：① 直接显示 → 被页面盖住看不见；② 先摘掉视图再显示 → 页面当场白屏。
Electron 的 `Menu.popup()` 是操作系统级弹窗，不受这个层级限制，所以走原生菜单。

### 键盘兜底：Ctrl+R / Ctrl+Shift+R

同时给店铺页面挂了快捷键（macOS 上走 Cmd）：`Ctrl+R` 重新加载、`Ctrl+Shift+R` 强制重新加载（忽略缓存）。

它是**兜底**而不只是"锦上添花"：右键菜单的触发依赖页面**没有**吞掉 `contextmenu` 事件——
若某个平台页面 `preventDefault()` 了它，菜单就不会弹（这是 Electron/Chromium 的既有行为）。
键盘走 `before-input-event`，在页面拿到按键**之前**由主进程处理，不受页面脚本影响。
工具条上原有的 ⟳ 也仍然可用。

## 上一版（0.4.30）：快手小店达人邀约真机实测——修掉 3 个真缺陷，真实发出邀约

**结论先说**：快手邀约现在能真的发出去（实测「我的达人 → 邀约中」新增 21:26 一条待处理记录）。
过程里发现并修掉 3 个此前没暴露的真缺陷，其中两个会让**整轮跑不通却不报真因**。

### 缺陷 1：页面被遮挡时 rAF 停摆 → 类目级联弹层停在屏幕外

快手的「带货类目」是级联弹层，它靠 `requestAnimationFrame` 计算定位。而 Chromium 在页面
不可见/窗口被遮挡时会**停掉 rAF**（实测：`visibilityState=visible` 下 rAF 触发 **0 次**、定时器正常）——
于是弹层永远停在初始的 `-9999,-9999`，子类「纸品湿巾」整块在视口外，受信任鼠标点不到。
此前引擎把它报成 `TASK_TARGET_COVERED: 被「unknown」遮挡，请把店铺窗口拉宽一些`，
把人往"窗口太窄"上引——**实测与宽度无关**（加到 1320 也一样）。

修法（两条，都对用户有用）：
1. `WebContentsView` 与独立窗口都关掉后台节流（`backgroundThrottling: false`）——定时器不再被降频。
2. **把"元素在视口外"与"被遮挡"分开报**：新增 `TASK_TARGET_OUT_OF_VIEWPORT`，消息直接说清
   「位置在视口外（矩形 …, 视口 …），多为平台弹层依赖 rAF 定位但页面被节流或弹层未展开；
   可先让店铺窗口处于前台再重试」。该报错**快、准、可操作**，不再含糊成"窗口太窄"。

> 也试过"离屏时降级为 JS 点击"，**实测有害、已回退**：JS 点击虽能触发，平台却只记下一级类目
> （标记里没有「纸品湿巾」），会被后面的校验拦下——把"点不到"变成"校验超时"，诊断更难。

### 缺陷 2：点「发送邀请」后平台弹「邀约提示」，没人点掉 → 抽屉永不关闭

真机实测：点「发送邀请」后平台弹**「邀约提示」**，逐条列出"该商品与这位达人不匹配"的项
（佣金率低于达人下限 / 商家体验分低于达人设置下限），底部按钮是「返回调整 / **继续发送邀约**」。
**不点它，邀约抽屉永远不关、一条都发不出去**；而档案里 `postSendConfirmText` 是空的，
所以此前整轮卡在 `waitForGone` 白等 180s 才超时。

修法：档案新增 `postSendConfirmTexts`（可多条，逐个条件点击），快手登记
`['继续发送邀约', '确认']`。同时把"抽屉收起超时"独立成 `postSendGoneTimeoutMs`——
不再用"有没有配确认框"去推（那样一配就把 180s 缩成 60s，反而让快手必然超时）。

### 缺陷 3：平台**明说**失败了，却被当成"平台还在处理"

发送失败时，快手**故意留着抽屉**（让你调整后重试），所以"抽屉没关"既可能是失败、
也可能只是平台在处理——`waitForGone` 根本区分不出来，只能含糊超时。

修法：新增引擎原语 **`requireTextAbsent`（文案缺席断言，读型）**：页面上出现指定文案即按
`code` 如实失败，并带上平台原文。快手在发送后、等抽屉收起**之前**插入这道断言，
文案用**「部分**邀约发送失败」——注意措辞：

> 实测同批 2 位里 **1 位进了「邀约中」（真的发出去了）**、1 位被拒（"近7天有未处理/被拒绝的邀约单"）。
> 所以错误码是 `TASK_SEND_PARTIAL`、提示语明说"**本批其余人可能已发出**，请以「我的达人 → 邀约中」
> 为准，别急着重发"——绝不能写成"未产生有效邀约"，那会误导用户重发、造成重复邀约。

### 真机验证

- **真实发出**：修复后实跑，「我的达人 → 邀约中」新增 **21:26 待处理**一条（达人「星星」，
  ID 233041797），与该轮运行时间、所选类目（零食饮料）对得上。
- **被拒绝的那一位如实报出**：同批另一位被平台以"近7天有未处理/被拒绝的邀约单"拒绝，
  引擎报 `TASK_SEND_PARTIAL` 并把平台原文一并记录（不再含糊超时，也不谎报全失败）。
- 彩排（不发送）全 31 步跑通，留档截图显示抽屉里联系方式/合作标签/带货描述齐备、
  额度「今日剩余99条」，停在「发送邀请」之前。
- 单测 125 项全过；`tsc --noEmit` 无错。

### 使用提示（重要）

- 快手这一类**级联弹层靠 rAF 定位**，页面被遮挡时可能定位失败。跑快手邀约时
  **请把店铺窗口保持在前台**（不要被其他窗口盖住）；若报了 `TASK_TARGET_OUT_OF_VIEWPORT`，
  按提示把窗口切到前台再重试即可。
- 平台对"近 7 天有未处理/被拒绝邀约单"的达人会**拒绝重复邀约**。这是平台规则，
  不是软件问题——届时引擎会如实报 `TASK_SEND_PARTIAL` 并列出是哪几位。

## 上一版（0.4.29）：把"跑了一半的邀约"说清楚——已发出的位数不能再看不见

承接 0.4.28 的微信邀约修复。修完之后发现还差一块：**部分成功时，战绩在界面上是看不见的。**

### 问题

邀约循环的进度汇总（完成轮数 / 跳过记录 / 停止原因）**只在整步成功时才落库**。
于是"跑完 24 轮、第 25 轮因为模型超时失败"这种情况，那 24 位**已经真实发出去了**，
但界面上既没有"成功邀约 24 位"，也没有失败原因里的一点提示——用户看到的就是一句
"步骤失败"，很容易理解成"一位都没发出去"。

**这恰恰是最需要看到计数的场景**：真实批量本来就会因为额度/候选耗尽而收尾，
中途因外部因素（模型超时、平台限流）中断时，用户必须知道"到底发出去了几位"。

### 改法

1. **loop 中途失败时，先把这一轮的进度落库再抛错**：payload 里带上
   `completedRounds` / `stopReason` / `failedRound` / `failedChild` / `rounds`（含跳过记录）。
   落库失败不影响原始错误向上抛（不能因为写日志掩盖真因）。
2. **面板如实说明"这是部分成功"**：邀约记录的 loop 行现在会写
   `成功邀约 24 位 · 跳过 3 位（不达合作门槛 / 7 天内已邀约过）· 第 25 轮失败——已完成的 24 位是真发出去了的`
   ——与"正常收尾"用不同措辞区分开，不会让人误以为整批作废；
   一位都没成功时则直接写「第 N 轮失败，没有发出任何邀约」。

### 验证

- 沿用 0.4.28 那次真实的 24 位运行数据校验：摘要能从落库的 loop payload 正确算出
  `成功邀约 24 位` + 跳过数 + 停止原因。
- 真机验证"失败路径落库"：造一条 2 轮循环、第 1 轮即失败的探针任务，落库结果里
  `completedRounds` / `failedRound` / `failedChild` / `stopReason` 齐备（此前这类 payload 根本不存在）。
- 面板实测：带「达人邀约 ·」前缀的探针任务出现在邀约记录里，展开后汇总行按预期渲染
  （实测输出 `成功邀约 0 位 · 第 1 轮失败，没有发出任何邀约`）。探针任务验证后已删除。
- 单测 118 项全过；`tsc --noEmit` 无错。

## 上一版（0.4.28）：修掉「微信小店邀约点了开始，一位都没邀出去」

**现象**：点「开始邀约」后应用跑满几分钟、看着一切正常，最后报失败，**一位达人也没邀约**。
真实记录：跑了 6 轮全部失败，报 `连续 6 轮命中 TASK_DAREN_PAGE_UNOPENABLE`。

### 根因：平台把"这位达人不能邀约"和"页面没渲染出来"表现成了同一件事

引擎对「详情页里找不到『邀请带货』按钮」只有一种解释：**页面（微应用）没渲染出来**，
于是按"退避后重试同一位"处理——连试 6 次都不成，判定"平台整体异常"整单失败。

但真机量取的实情是：**同一张详情页上，按钮在不在取决于这位达人本人**：

| 达人状态 | 页面上有什么 | 该怎么做 |
|---|---|---|
| 可邀约 | 蓝底「邀请带货」按钮 | 点它 → 进邀约表单 |
| **不达合作门槛** | **没有按钮**，写着「**暂未到达合作门槛**」（悬浮说明：成为热招品牌 / 店铺需满足店铺评分行业前30%） | **跳过换下一位** |
| **7 天内已邀约过** | 按钮**在**，但是灰色禁用态（悬浮说明：「你已经邀请过该达人，7天内不可再次发送带货邀约」） | **跳过换下一位** |

广场里这三种都有（实测一屏 20 位里前两位就是"不达门槛"）。
把前两种塞进"页面没渲染出来"这条路径，就必然变成"一直重试同一位"→ 耗尽次数 → 整单失败。
**这也是"一位都没邀出去"的直接原因**：24 位的量，卡在第 1 位就出不去。

### 修法（三处，都在引擎原语上，不写平台 if）

1. **`clickByText.absentText` + `absentCode`** —— 目标不在时，若页面上出现这段**替代文案**，
   就立刻按专属错误码失败，**不等到超时**。
   判据刻意收紧（见 `ABSENT_FN`）：只认"**本身就在说这句话**"的元素（自有文本命中，或整段文本
   不比那句话长多少）。不收紧的话任何祖先都会因为"后代里有这句话"而命中，判据就退化成
   "页面上出现过这几个字"——太松，容易误判。命中即返回，是因为"这位不可用"等多久都一样，
   而"页面没渲染出来"等一下还能好：**这两件事的处置相反，必须分开**。

2. **`loop.onCode.advance`** —— 新增的恢复语义：**重开本轮但保留"已访问"记录** = "跳过这一位、换下一位"。
   与既有的 `restart` 只差这条记录：`restart` 要**回滚**它才能在重试时再选中同一位（用于限流退避）；
   `advance` 要**保留**它，否则就是原地重试同一个人，永远走不出去。

3. **`disabledCode` 用上了**（这个字段本来就有）：详情页的「邀请带货」禁用 → 报
   `TASK_DAREN_ALREADY_INVITED`，同样按 `advance` 跳过换人。
   顺带让引擎**把平台给的禁用原因读出来**（按钮旁的 popover）写进错误消息——
   排查时"已邀约过"和"额度用完"是完全不同的处置，不该都显示成一句"平台限制该操作"。

### 顺带修掉：连续跳过撞满上限时不再报"平台整体异常"

`advance` 连续撞满 `limit` 时**干净收尾**（run 成功 + `stopReason` 如实记录），不报失败：
触发它的判据是平台自己写明的"不可邀约"文案，那是确定性信号、不是渲染故障——连续这么多位
都不可邀约，只能说明这组筛选下确实没更多可邀的人了，就该像"额度用完"一样停下。
（`restart` 那条仍然按失败处理：它更可能是平台整体不可用，静默跳过所有人不可接受。）

### 顺带修掉：一次模型抖动不该让整批已发出的邀约作废

真机跑到**第 25 轮**时 `aiGenerate` 超时 30s，整单报 failed——而前 24 位已经真实发出去了。
原因是 loop 的嵌套步骤拿不到 `retryLimit`（那个字段只作用于顶层步骤）。
现在子步骤声明了 `retryLimit` 就先重试它（AI 生成话术是幂等的：重跑只是重新生成覆盖同一个输入框，
所以给了 2 次）；非幂等的步骤（点击/输入）绝不重放，行为照旧。

### 面板：如实说出"跳过了几位"

逐位邀约时被跳过的达人不会出现在任何步骤成功里，用户只看"本次邀约 N 位"分不清
"跳过了 3 位"和"平台不给发了"。现在展开邀约记录的 loop 步骤会多一行：
`成功邀约 24 位 · 跳过 3 位（不达合作门槛 / 7 天内已邀约过）· 因「TASK_QUOTA_EXCEEDED」正常收尾`。

### 一句话教训（已写进代码注释）

**"找不到"是两种完全相反的事**：页面没渲染出来（等一等/换条件），与"这个对象天生不可用"（换下一个）。
平台用**替代文案**或**禁用态**表达后者时，引擎必须能认出来——否则就会把"没有可邀约的人"
误报成"平台故障"，或者更糟：一直重试同一个人直到整单失败。

1. **`clickByText` 支持"去空格后的文案"**：平台把按钮文案拆进子 span 并用 CSS 拉字距，

2. **`clickAll.skipSelector`**：表头的"全选"复选框与商品行同选择器时，把它排除掉

## 本次更新（0.4.26）：快手小店发票补齐 + 一个让"点页签"必然失败的引擎缺陷

上一版把微信/拼多多/抖店的多方向都打通了，快手还卡在"未登录"。用户登录后实测，又挖出三个真问题。

### 修掉：范围限定只认第一个容器 → "在页签里找文案"永远找不到

引擎的 `clickByText.within`（限定查找范围）旧实现是 `document.querySelector(w.selector)` ——**只取第一个匹配的容器**。而页签类容器的选择器天然命中多个（快手发票页 `.ant-tabs-tab-btn` 有三个），于是"在页签里找「处理中」"实际变成了"在**第一个**页签（未开票账单）里找处理中"，必然找不到：

```
TASK_SELECTOR_CHANGED: 页面上找不到文案为「处理中」的可点击元素
```

这句错话把人往"页面改版了"上引，真实原因却是我自己的范围逻辑写错了。改为返回**范围集合**（`__scopeRoots` + `__inScope`），每个命中的容器都算范围内；`climb` 也改成对每个容器各自上抬。这条修复同时影响抖店的类目筛选（同一个 `within` 机制）。

### 修掉：同名页签数据不同，切不动就会张冠李戴

快手发票页的「处理中」与「处理记录」**表头完全相同**（流水单号/账单编号/…/状态/操作）。切页签一旦静默失败，读回来的是上一个页签的数据，而按表头做的 `expectHeaders`/`rejectHeaders` 对这种情况**完全看不出来**——「处理中」会显示成「处理记录」的记录且毫无提示。

新增 `clickByText.verifyActive`：点完在页签容器里校验"文案匹配的元素带上了选中类"，超时没选中就报 `TASK_TAB_NOT_ACTIVE` 并中止。切不动就如实失败，绝不把邻居的数据当成这个页签的。

### 修掉：把"已提交、无需商家操作"的流水算进了"待开票"

快手「处理记录」实测是**审核通过**的流水，「处理中」是已提交等平台审核——这两类商家都没有待办动作。原样求和会让"待开票条数/可开金额合计"虚高（实测多算了 3 条 + ¥389.67）。

新增 `section.pending`（默认 true）+ `notPendingNote`。`pending: false` 的方向照常采集与展示，但标「无需操作」、**不计入**合计；界面上方另有独立一行说明有多少条属这类，避免用户以为"数字变少了是抓漏了"。CSV 导出保留全部方向（导出是留档，不是待办清单）。

### 修掉：平台重复渲染导致单元格把同一段文案显示两遍

快手的账单月份单元格 `innerText` 是 `"2026年01月\n\n2026年01月"`（平台为响应式/tooltip 渲染了两份），界面上显示成"2026年01月 2026年01月"。新增 `normalizeCellText`（主进程映射与界面显示**共用同一口径**）：压掉内部换行/多空格；整串正好是同一段重复两遍时只留一遍。规则保守——**每半段至少 2 字符**才判重复，否则「人人」这类叠字会被误削。

## 本次更新（0.4.25）：发票中心「两个方向都抓」——修掉一个让多方向采集全盘失效的真实缺陷

起因是一个很直接的问题：**「给平台开票」和「给买家开票」是不是都抓到了？** 如实回答是只抓到一个。这版把两个方向都做成真的能抓，并顺带修掉了一个更隐蔽的缺陷。

### 修掉的核心缺陷：采集任务在"自己的弹层"里跑，视图被摘掉 → 每个方向切换都失败

发票中心是从弹层（modal）里发起的，而弹层一打开就会把店铺的原生 WebContentsView 从窗口上**摘除**（避免原生层盖住弹窗）。被摘之后页面文档视口变成 `0×0`：元素还在、也还有尺寸，但坐标全在视口外，`elementFromPoint` 恒为 `null` —— 受信任鼠标**物理上到不了页面**。

于是实测现象是一连串让人误判的错误：

```
TASK_TARGET_COVERED: 「给平台开票」被「unknown」遮挡，点不到——请把店铺窗口拉宽一些让页面不再重叠后重试
TASK_TARGET_COVERED: 「给消费者开票」被「unknown」遮挡，点不到
TASK_TARGET_COVERED: 「可开票」被「unknown」遮挡，点不到
```

它把人往"窗口太窄、布局重叠"上引，实际跟窗口宽度毫无关系。实测确认：视图摘除状态下**页面脚本照常工作**（JS 多级点击 3 秒内就把对方数据切出来了，表头多出「处理状态/操作」、行数 5 → 2）。

修法分两路，都不是"一律降级为 JS 点击"这种会埋雷的做法：

1. **新增错误码 `TASK_VIEW_DETACHED`**：检测到视口退化且步骤没声明允许降级时，立刻如实报出"视图未挂载"，而不是等超时再给一句含糊的"找不到元素"（覆盖 `typeText`/`ensureRows`/`ensureRowsById` 等需要真实落点的步骤）。
2. **新增步骤选项 `clickByText.allowJsWhenDetached`（默认 false）**：只给**纯页内状态切换**的点击开（切页签/切筛选——点了之后页面自己重渲染，不依赖浏览器输入管线）。依赖框架真实输入的按钮（微信邀约表单）绝不开启：合成 click 对它们不生效，开了会静默点空、把根因推到后面几步才暴露。

### 开票方向真的分开了（不是把同一张表读两遍）

- **微信小店**：3 个方向。`申请平台开票` 5 条、**`给平台开票` 2 条**（表头多「处理状态」，两批 id 完全不同）、`给买家开票` 实测整页无表 → 0 条。
- **抖店**：实测有**四个**方向（不是两个）。`我给平台开票` 1 条、`给消费者开票` 0 条、`平台给我开票` **37 条**、`达人给我开票` 0 条。
- **拼多多**：`给买家开票（订单开票）` 3 条 + **`给平台开票（资金中心）`** —— 后者在**另一个站点**（cashier.pinduoduo.com），页面上是**卡片不是表格**。
- **快手小店**：`给平台开票（未开票账单）` 5 条，需先重新登录（见下）。

支撑这些的能力（都在档案里按实测登记，`packages/shared/src/constants/invoice.ts` + `invoice-steps.ts`）：

- `sections[]` 多方向 + 每方向独立指标名（互不覆盖）；
- `section.pageUrl`：方向在另一个页面 → 先导航过去；
- `section.labels[]`：方向是"标签 + 值"卡片而非表格 → 逐个标签读值拼成一行（`readLabelValue` 新增 `allowText`，公司名与「2026年05/06/07/08月」这类文本不再被数值抽取截断或判失败）；
- `expectHeaders` / `rejectHeaders`：切页签没生效时会读到**上一个方向**的表 —— 用实测列名把那种情况挡掉（微信靠「处理状态」、抖店靠「收票方主体 ↔ 开票方主体」互为邻居判据），绝不把上一个方向的数据重复挂到本方向名下发出去；
- `emptyOk`：实测 0 条的方向本来就没表，落一条**空快照**（如实显示 0 条），不再把整轮采集判失败。

### 顺手修掉的数据质量缺陷（都是实测踩到的）

- **重复表头行被当成记录**：抖店「平台给我开票」第一行数据位置又是表头文案，被统计成 1 条"账单名称/账单类型"的记录。清洗后 37 条（原 38）。
- **空态占位行被当成记录**：抖店「给消费者开票」没数据时渲染一行「暂无数据」，被算成 1 条待开票。
- 清洗判据只看文案不看类名（整行都是空态词 → 丢；非首行且 ≥60% 单元格与表头文案相同 → 丢），实现提为 `TABLE_ROW_CLEAN_FN` 由引擎注入并**被单测直接执行同一份源码**，避免"单测过了、注入的那份没改"。
- **快照显示的失败是旧的**：界面会一直挂着"上次采集失败"，哪怕后续已经成功。改为取该店**最近一次**运行、只有它确实失败才回报。
- **登录态失效被报成含糊的超时**：快手被重定向到登录页时，`waitForPage` 只会给一句"超过 45000ms"，让人以为是页面慢/改版。新增 `TASK_LOGIN_REQUIRED`，直接说明"被重定向到登录页，请重新登录"，界面并给出「去登录」按钮。

上一版把会话 Cookie 做成了自动持久化（重启不再丢登录态），但实测发现恢复时**悄悄放宽了作用域**：微信的登录凭据（`biz_token` 等）是 **host-only** Cookie（`store.weixin.qq.com`，只对该主机生效、不带前导点），恢复后却变成了**域 Cookie**（`.store.weixin.qq.com`，对整个子域生效）——凭据可能被发往子域，属于安全上的放宽，而且平台判重时也可能因此认不出原会话。

修法：恢复时**区分两种形态**——带前导点的才传 `domain`（域 Cookie），host-only 的不传 `domain`，交由 `url` 决定（Chromium 就存成 host-only）。

真机验证（强杀进程 → 重启）：写入 host-only 会话 Cookie → 恢复后 `domain` 仍是 `hostonly-probe.test`（无前导点）、值完全一致 ✓。

同时清理了修复前产生的脏快照（那批被放宽的 Cookie），避免旧数据一直被恢复。

**验证过但未改代码的一项**：用户主动「清 Cookie」时会**同步删除会话快照**（否则下次启动会把刚清掉的登录态灌回来）——实测清空后快照文件确实被删、Cookie 归零 ✓。

## 上一版（0.4.16）：重启不再丢登录态 + 微信邀约全量测试修掉 4 个真缺陷

### 一、重启应用不再需要重新扫码登录

之前每次重启都要重新扫码，真实原因终于查明并修掉：

**根因**：微信小店的登录凭据（`biz_token` / `biz_ticket` / `device_id` 等）**全部是会话级 Cookie**——实测该分区 8 条 Cookie 的 `session` 标记全为 true。而 Chromium **默认不把会话 Cookie 写入磁盘**（分区目录下的 Cookies 库里 0 行持久记录），所以哪怕分区用的是 `persist:`，进程一退登录态就没了。

这跟"服务端会话短"是两回事：登录期间实测 **121 分钟不掉线**，纯粹是客户端没保存。

**做法**：把会话级 Cookie 加密快照到磁盘，下次启动灌回分区。

- **只存会话级**：有到期时间的 Cookie 本来就由 Chromium 落盘，不重复存；
- **DPAPI 加密**（Windows 数据保护）后才落盘；系统加密不可用时**拒绝明文写**，只告警；
- 先写临时文件再改名，中途被杀不会留下半截文件（解不开＝白丢登录态）；
- **三条触发路径**兜住各种退出方式：Cookie 变化即防抖快照（3 秒）/ 每 60 秒定时 / 退出前快照；
- 退出前快照带 **3 秒超时兜底**，避免快照卡住导致"点了退出退不掉"；
- 用户主动清 Cookie 时同步删除快照，否则下次启动会把刚清掉的登录态灌回来。

**真机验证（用强杀进程模拟最恶劣情况，不走任何退出钩子）**：写入一条会话级 Cookie → 强杀 → 重启 → 读回**值与写入时完全一致** ✓；顺带确认 `biz_token`/`biz_ticket` 等微信凭据同样在快照范围内 ✓。

## 上一版（0.4.6）：修复「点开始邀约就失败」

### 现象与定位

你反馈点「开始邀约」后失败。运行记录：**第 1 轮的子步骤 3（点主推类目 chip）** 就报错
`找不到「个护家清」的限定范围（{selector: ".quick-filter-button-enums"}）`，且一个步骤结果都没留下。

根因是 0.4.5 引入 `within`（限定范围）时的一个缺陷：**"范围容器找不到"被写成了立即失败**，
而导航刚完成时达人广场的筛选区往往还没渲染出来（SPA 要挂载一小会儿）——第一下点击撞上空窗期，
整个运行当场失败。就算撞过了这一步，下一步点级联叶子「不限」也会以同样方式失败（级联弹层要点完
chip 才出现）。0.4.5 真机验证时没暴露，是因为当时页面早已加载完成（热页面），没有踩到冷启动的时间窗。

### 修法（两处）

1. **SCOPE_NOT_FOUND 改为在超时内轮询等待**（和"元素没找到"同一待遇）：每 300ms 重找一次范围容器，
   等它随页面渲染出现；整个超时内都没出现才报 `TASK_SELECTOR_CHANGED`，且错误消息会写明

## 上一版（0.4.0）：拼多多——实测确认不可自动读取，改为「手动录入」

### 实测结论：拼多多的数字在 DOM 与接口里都是混淆码位

本次把拼多多挖到底了，三条证据：

1. 页面会先请求 `api/phantom/web/en/ft` 取回 **`web_spider_rule`（带种子的规则串）+ 专用字体 `ttf_url`**，再用该字体渲染数字；
2. **DOM 里不是数字字符**：指标值元素是 `class="value … __spider_font"`、`font-family: spider-font`，读到的是私有区码位（实测只有"较上期 X%"这类百分比可读）；
3. **接口 JSON 里也是混淆的**：数据中心自己的响应里 `"payOrdrAmt":"…"`、`"prevYearTotalSalesAmount":"…"` 的值同样不是数字字符。

也就是说，"读接口"和"解字体"都等于**持续对抗平台明示的反自动化措施**（规则串按会话下发种子、字体带内容哈希）。**本应用不做这种绕过**——这是产品红线，不是技术做不到。

## 上一版（0.2.4）：卡死 / 闪退 / 崩溃专项排查与修复

**排查方法**：先把近三天应用日志做模式归类（异常/渲染进程消失/未处理拒绝），再对当前进程内存与标签页数量取证，最后用独立临时实例做"故障注入"复现验证。

### 1. 卡死：日志写入的异常递归风暴（真实故障，已复现并根治）

日志证据：`2026-09-13 18:11` 的 **8 秒内 11,787 条 `uncaughtException: EPIPE: broken pipe`**（约 1,470 次/秒，CPU 被异常处理打满，表现就是"卡死"）。

根因链：应用从已关闭的终端/shell 启动 → stdout/stderr 管道断开 → `logMain` 末尾**未加保护的 `console.error` 抛 EPIPE** → 全局 `uncaughtException` 处理器又调用 `logMain` 记录它 → 再次 console.error → 再次抛错 → **无限递归**。

修复：
- `logMain` 的控制台镜像写入加 try/catch，并在首次失败后**永久熔断镜像**（文件日志不受影响）；
- 同时监听 stdout/stderr 的 `error` 事件，把异步 EPIPE 在源头吞掉；
- `uncaughtException` / `unhandledRejection` 处理器改为**绝不抛错**的写入路径，并加**限流**（同类异常 10 秒内最多记 20 条 + 1 条汇总），避免日志自身把磁盘/CPU 打满。

验证（故障注入）：从脚本以管道拉起应用 → 销毁管道 → 注入 60 次渲染层错误 → **`uncaughtException=0`、应用存活**（旧代码同触发 1.1 万条）。

### 2. 闪退/白屏：渲染进程崩溃无留痕、无恢复

- **店铺标签页崩溃**：此前只弹一个 toast，日志里查不到（此前诊断只能靠猜）。现在写入 `store tab renderer gone store=/tab=/reason=/url=`，并**有界自动重载**（同一标签页 5 分钟内最多 1 次，防"崩溃-重载"死循环）。
- **主窗口渲染进程崩溃**（用户看到的"闪退/白屏"）：此前只记一行日志。现在**自动重载最多 3 次/5 分钟**；超过则停手并弹窗如实告知（附导出诊断指引），不做无限重载。
- **无响应（"卡死"）留痕**：主窗口与店铺标签页都监听 `unresponsive`/`responsive` 并写日志——这类问题事后只能靠日志定位。

验证（故障注入）：对店铺标签页与主窗口分别发 CDP `Page.crash` → 两者都**留痕 + 自动恢复且恢复后可用**。

### 3. 内存持续增长：任务运行标签页按店铺复用

取证：实测运行数小时后有 **10 个渲染进程、合计约 1.5GB**。原因：任务引擎**每次运行都新建一个标签页且从不回收**（验收过程中一天内堆了 7 个达人广场标签页）。

验证：同一店铺连续跑两次任务，标签页数量 `2 → 3 → 3`（不再增长）。

## 能力总览（M0–M4）

### 会话与 Cookie
- **会话导出/导入加密包**：导出经 scrypt（N=16384, r=8, p=1）+ AES-256-GCM 加密的 `.shopilot` 包，内含 Cookie 清单与店铺环境指纹配置；包携带有效期（默认 30 天），过期包一律拒绝导入。
- 口令由**主进程托管的独立窗口**采集（确认框 + 双次输入），不经过 Renderer，也不走业务 IPC 通道。
- 导入为覆盖语义：先清空目标店 Cookie 再写入；篡改包（GCM 认证失败）与结构异常包均拒绝导入，且**绝不动目标店现存会话**。
- **Cookie 查看器**：列表（值仅预览、HttpOnly/Secure 如实标记）、按名称/域搜索、单条删除、清空全部。
- 已知边界：导出包仅含 Cookie + 环境配置；**localStorage/IndexedDB 不在包内**；包为跨机传输设计（Cookie 为明文清单，安全性由容器口令加密保证）。

### 应用锁
- 主密码校验信息为 scrypt 派生值，整体再经系统 safeStorage（DPAPI）封装，**磁盘上不存在明文密码或明文校验值**。
- 锁定后：隐藏店铺浏览器视图、销毁代理认证等敏感引用、并**门禁全部业务 IPC**（仅解锁与状态查询可用）。
- 解锁需主密码；错误密码计次并写审计。空闲（5/15/30/60 分钟可选）自动锁定；`Ctrl+Shift+L` 可随时锁定。

### 代理健康巡检
- 绑定代理即刻体检、店铺浏览器打开时复检过期绑定、后台每 5 分钟巡检已绑定代理，状态变化通过 `proxy:healthChanged` 推送界面。
- 规范红线：**代理不可用时不自动切换、不静默降级**，只在界面如实展示失败原因，由用户决定。

### 备份与诊断
- **诊断包**（§22 脱敏）：版本、系统、数据库迁移版本与规模、代理体检摘要、白名单设置键、审计最近记录、脱敏日志；**不含** Cookie 值、代理凭据、会话原文、主密码信息。
- **审计日志导出**：JSONL 全量导出（可按条件过滤）。
- **运行/崩溃日志**：`userData/logs/app-YYYY-MM-DD.log` 按天落盘，单文件 5 MB 轮转（`.log.1`），**默认保留 14 天**并在启动时清理更早文件，敏感字样行整行掩码，renderer 错误与未捕获异常统一落盘。

## 已知边界（如实声明）

- 备份包跨机恢复覆盖元数据、配置与标签索引；**登录态**需在目标机重新登录，或经会话导出加密包导入（DPAPI 边界）。
- 任务引擎为**全局串行队列（并发=1）**；跨进程原地恢复不支持；人工确认节点默认 60 分钟超时。
- 截图步骤要求店铺浏览器处于可见视口，否则如实报 `CAPTURE_EMPTY` 失败。
- 安装包未做代码签名（无证书），Windows 可能提示"未知发布者"；自动更新仅做 SHA-512 哈希校验、无签名校验（INTERNAL_BUILD 边界）。
- **AI 请求由主进程直连出网、不走店铺代理**（Chromium 的 session 代理管不到主进程 fetch）；接口地址须 https://（仅本机 127.0.0.1 / localhost 允许 http://）。API Key 只在主进程使用，界面与诊断包都不会带出。
- **邀约抽屉里的"推荐商品"区域没有稳定选择器**（平台用哈希类名）：AI 模式默认读"话术框所在固定定位浮层"的可见文本；读不到就如实失败，不会拿整页文本充数。
- 自动更新内容托管于 GitHub Releases（**v0.1.5 已发布**：安装包 + blockmap + `latest.yml`，`node publish-release.js` 幂等上传；发新版本前先改 `package.json` 的 version 再跑 `pnpm run release:full`）；仓库已设为 **public**，打包态匿名在线检查实测通过（同版本如实返回"已是最新"）。启动自动检查默认关闭，可在设置 →「关于软件」开启。

## 回滚

- 保留上一版本安装包即可回退：卸载当前版本 → 安装旧版。数据库迁移为向前兼容（schema 版本仅升不降），回退到更早版本前请先备份 `userData`。
- 版本与产物校验：以 `release/release.json` 中的 SHA-256 为准核对安装包完整性。
